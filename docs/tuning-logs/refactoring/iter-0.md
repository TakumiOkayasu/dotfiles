# iter 0 — refactoring (description/body 整合チェック)

静的レビュー（dispatch なし）。SKILL.md の frontmatter `description` と body の主要要素が整合しているか、隣接スキル（interface-first-design / tdd / test-coverage-guard / systematic-debugging）との重なり語が body 側で整理されているかを確認する。

## description

> 振る舞いを変えずにコード構造を改善する際に使用。

短い1文。要素は **3つ**:

1. 「振る舞いを変えない」
2. 「コード構造を改善」
3. 「使用する場面 = 改善する際」

## body との突き合わせ

| description 要素 | body での出現箇所 | 整合 |
|---|---|:---:|
| 振る舞いを変えない | L29「鉄則: 振る舞いは変えない」、L52「変更前後でインターフェース同一」、L98「振る舞いの変更 → 禁止」 | ✅ |
| コード構造を改善 | L8「Refactoring」見出し、L56-92「コードスメル」セクション（長いメソッド/条件分岐/マジックナンバー） | ✅ |
| 使用する場面 | L8-15「トリガー条件」（リファクタ指示・スメル解消・PR指摘・下準備） | ✅ |

description は最小だが body との乖離はない。**ただし以下の暗黙仕様が description から読み取れない**:

| body にあるが description に無い要素 | 影響 |
|---|---|
| 前提条件「テスト存在 + 全 PASS」（L19-25） | テストなし状態で発動依頼された時の判断が description だけだと不能 |
| 禁止「テストなしで進める」「複数スメル同時」「無関係コード変更」（L96-105） | 「ついで修正」誘惑への抵抗の根拠が body 側にしかない |
| 「特性テスト」への言及がない（テストが薄い既存コードのリファクタ前提テスト追加手順） | レガシーコード対応の裁量補完が起こり得る |

## 隣接スキルとの重なりチェック（trigger-overlap.md 参照）

| 重なり語 | 隣接スキル | 危険度 | refactoring description での扱い | 評価 |
|---|---|:---:|---|:---:|
| **改善** | empirical-prompt-tuning | 🟢 低 | 「コード構造を改善」で対象ドメイン明示 | ✅ |
| **構造** | consultation | 🟢 低 | 「コード構造」と限定 | ✅ |
| (暗黙) **設計** | interface-first-design | — | description 上は「振る舞いを変えずに」で **新規設計を除外** している | ⚠️（暗黙） |
| (暗黙) **テスト** | tdd / test-coverage-guard | — | description 上は無言。body 内「前提条件」は明確だが description だけでは見えない | ⚠️（暗黙） |

**潜在曖昧点**:

- **R-0-1**: description が短すぎて、body の「テスト前提」「振る舞い不変」が **subagent が SKILL.md 全文を読まないと分からない**。description だけ読んだ subagent が「テストない状態でリファクタしてくれ」と言われたとき、body のガード節を発動するかは body 読了に依存
- **R-0-2**: description に「interface-first-design / tdd への委譲条件」が明示されていない。新規設計依頼や新規実装依頼での誤発動可能性
- **R-0-3**: body L96-105 禁止事項に「振る舞いの変更」「ついで修正」が並ぶが、**「ついで」の典型ケース**（バグ修正混入・仕様変更混入）の例示が薄い。シナリオC で実害化を要観察
- **R-0-4**: 「特性テスト」（characterization test）への参照なし。テストが薄い既存コードのリファクタ手順（テスト追加 → リファクタ）の道筋が body 側にもない
- **R-0-5**: フェーズ2「スメル特定 → 優先度順」の **優先度の判断基準** が「影響範囲小・リスク低」のみ（L41）。複数スメル並列時の絞り込み裁量補完が起こり得る
- **R-0-6**: 出力形式（L114-128）の「振る舞い保証」項目が「インターフェース変更: なし / あり（要確認）」の2値。**実際にどう保証したか**（テスト全 PASS の根拠 / behavioral diff の確認方法）の記載なし

## iter 1 で観測したい焦点

| 焦点 | 期待される観測 |
|---|---|
| シナリオA で「振る舞い不変」「1スメル1変更」「都度テスト」が自然発動するか | description 短いので body 読了の質に依存 |
| シナリオB で前提条件違反を **拒否** するか、または条件付き受諾するか | R-0-1 の実害判定 |
| シナリオC で「ついで修正」を **明示分離** できるか | R-0-3 の実害判定 |
| 出力形式（L114-128）の「振る舞い保証」項目を subagent が埋められるか | R-0-6 の実害判定 |
| **tool_uses 偏り**: シナリオ間で 3-5 倍の差があるか | references descent の有無 |

## 結論

description / body の主要要素に明示的乖離なし。ただし description が 1 行と最小のため、body 側の前提条件・禁止事項への依存度が高い。iter 1 では **body 全文読了下での自然発動の質** を主要観測対象とする。description 改訂は iter 2 以降の実害観測後に判断。
