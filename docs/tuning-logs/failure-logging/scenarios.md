# failure-logging シナリオカタログ

empirical-prompt-tuning でチューニングするための評価シナリオ。**iter 開始後は変更しない**。

- 対象スキル: `claude/skills/failure-logging/SKILL.md`
- description: 「エラー発生時、アプローチ失敗時に使用。失敗DBを構築し同じ失敗を繰り返さない。」
- 収束目標: **連続2** イテレーション（典型スキル）

## 隣接スキルとの境界（iter 0 整合確認の焦点）

| スキル | 対比 |
|---|---|
| systematic-debugging | systematic-debugging = 失敗**分析**（4フェーズ根本原因）、failure-logging = 失敗**記録 / 履歴参照**。同時発動あり得るが責務は直交 |
| consultation | consultation = 判断迷い時の技術相談、failure-logging = 既に起きた失敗の記録。発動条件が異なる |
| tdd | tdd = テスト駆動実装、failure-logging = 失敗の DB 化。テスト失敗は本 skill のトリガー対象だが、修正着手は tdd が担う |

trigger-overlap.md では「失敗」語で **🟢 低リスク**（systematic-debugging = 分析 / failure-logging = 記録 で対象ドメインが別）と判定済。iter 0 で境界明文化が必要か再確認する。

## Baseline シナリオ

### シナリオA（中央値: コマンド失敗 → 記録 → 次アプローチ）

**状況**:
ユーザーが `docker compose up -d` で Web アプリを立ち上げようとしたが、`Error response from daemon: Conflict. The container name "/app" is already in use by container "abc123"` が返ってきた。ユーザーは「立ち上がらない、別の方法で試して」と依頼。`claude_tmp/failure_log/` ディレクトリには既に `1-100-fail.md` が存在し、末尾エントリは `## 47`（解決済みではない）。

**要件チェックリスト**:
1. [critical] **失敗を記録する前に次アプローチへ進まない**（SKILL.md L10-16 トリガー「コマンドがエラーになった時」 + L103 禁止事項「失敗を記録せずに次へ進む」）
2. [critical] **連番を 48 とし、`1-100-fail.md` に追記する**（SKILL.md L23「既存ファイルの最大連番から継続」、100件未到達なので新ファイル不要）
3. フォーマット準拠: 「何をしようとしたか / 試した手法/コマンド / 結果 / 原因（明確な場合のみ）」の 4 項目（SKILL.md L42-48）
4. 原因が明確でない場合は原因欄を空欄または「不明」と記載し、**推測で埋めない**（SKILL.md L106）
5. フェーズ2: 次アプローチ選定前に `claude_tmp/failure_log/` の関連エントリを検索する（SKILL.md L54-62）
6. 出力形式: `✅ 失敗記録: claude_tmp/failure_log/1-100-fail.md #48`（SKILL.md L85-88）
7. 次アプローチ案で過去の失敗手法を除外する（今回なら「名前衝突」系の再試行を避ける）

### シナリオB（edge 1: `/compact` 後 + 新アプローチ着手）

**状況**:
セッションが `/compact` された直後、ユーザーから「さっきの続き、ファイルアップロードのバグ直そう」と依頼。会話履歴は要約済みで、直前に試したアプローチの詳細は失われている。`claude_tmp/failure_log/` には `1-100-fail.md` と `101-200-fail.md` が存在し、合計 137 件のエントリ。

**要件チェックリスト**:
1. [critical] **新アプローチ着手前に履歴参照を実施する**（SKILL.md L15 トリガー「新しいアプローチを試みる直前」 + L16「`/compact` 後」、L104 禁止事項「履歴を読まずに同じアプローチを試す」）
2. [critical] **`claude_tmp/failure_log/` 内の全ファイル列挙 → 関連キーワードで絞り込み**（SKILL.md L56-58）
3. 「ファイルアップロード」「upload」「multipart」等のキーワードで絞り込み方針を提示する
4. `✅ 解決済み` マークの有無を確認する（SKILL.md L60）
5. 過去の失敗手法を除外した上で新アプローチを選定する（SKILL.md L62）
6. 出力形式: `📋 履歴確認済み: [件数]件の関連失敗を確認。除外手法: [手法名]`（SKILL.md L93-95）
7. 推測で「こうだろう」と修正に着手しない（履歴参照前の着手は禁止事項違反）

### シナリオC（edge 2: 既存エントリの解決 → 更新）

**状況**:
前回セッションで「`bun install` がネットワーク不通で失敗」を `claude_tmp/failure_log/1-100-fail.md` の `## 72` に記録済み（解決済みマークなし）。今回セッションで、ユーザーが VPN を有効化した結果 `bun install` が成功したと報告。「さっきの失敗、解決したから記録を更新して」と依頼。

**要件チェックリスト**:
1. [critical] **フェーズ3 の手順に従い、既存エントリに `✅ 解決済み` マークと解決方法を追記**（SKILL.md L66-79）
2. [critical] **既存エントリのフォーマットを変更しない**（SKILL.md L107 禁止事項「フォーマットを変更する」。解決方法欄の追加は L78 の拡張フォーマット準拠）
3. 解決エントリのフォーマット: 「何をしようとしたか / 試した手法/コマンド / 結果 / 原因 / 解決方法」の 5 項目（SKILL.md L73-79）
4. 既存の「何をしようとしたか」「試した手法/コマンド」「結果」「原因」は書き換えず、`✅ 解決済み` マークと「解決方法」行のみ追加する
5. `## 72` のヘッダ行を `## 72 ✅ 解決済み` に更新する（SKILL.md L73）
6. 連番は変更しない（72 のまま）

## Hold-out シナリオ（収束判定時のみ使用）

### シナリオD（誤発動回避: バグ原因分析依頼 → systematic-debugging 領域）

**状況**:
ユーザーから「`user.service.test.ts` が落ちてる。なぜ落ちてるか調べて原因を教えて」と依頼。失敗は今回 1 回目で、claude_tmp/failure_log/ にはまだ関連エントリはない。ユーザーは修正実装ではなく**原因の説明**を求めている。

**要件チェックリスト**:
1. [critical] **本スキルの中核発動ではなく `systematic-debugging` への委譲を明示する**（failure-logging は記録、分析は systematic-debugging。trigger-overlap.md 🟢 低リスク行の境界）
2. [critical] **失敗エントリの新規作成（フェーズ1）を本依頼の主要対応にしない**（ユーザー依頼は「原因究明」であり「失敗DB構築」ではない）
3. 失敗発生の記録自体は本スキルで可（トリガー L12「コマンドがエラーになった時」該当）、ただし中核対応は systematic-debugging の 4 フェーズに引き継ぐ
4. 2回以上つまずいた時に本スキルを再発動する可能性を予告しておく（SKILL.md L14）
5. 履歴参照（フェーズ2）は「関連する過去失敗がないか」の補助的チェックとして実施可、ただし主対応にはしない
6. 推測で原因を記録しない（SKILL.md L106）

## 運用メモ

- シナリオ A は「コマンドエラー」で最も典型的な発動。連番の継続規則と禁止事項「失敗を記録せずに次へ進む」の両方を試す
- シナリオ B は `/compact` 後の再開トリガーと履歴参照フローの組み合わせ。複数ファイル列挙が発生するので `tool_uses` が増えやすい
- シナリオ C は既存エントリの in-place 更新で、フォーマット維持の禁止事項が主眼。シナリオ B の「履歴参照」との役割分離も観察点
- シナリオ D は hold-out として、**「失敗」語だけで本スキルを早合点せず systematic-debugging に委譲する**判断を試す
