### 採用理由

- **PO-1-B-2（観測 vs 修正の境界）は境界節で最も直接解消できる**。「観測（読み取り）は前提条件下でも可 / 変更適用はステージング検証必須」を 1 行に圧縮可能。
- **PO-0-1（iter 0 事前予想: 隣接スキル境界節不在）を先取り解消**。iter 1 で直接表面化しなかったのは subagent が裁量で埋めたためで、潜在的曖昧は残存。
- **hold-out D（バグ修正 = 非発動判定）の誤発動阻止コスト低減** が期待できる（他スキル hold-out と同型の成功パターン）。
- **5 スキル連続で上振れ波及**（refactoring / consultation / iface-first / e2e-browser / qa-nightmare の iter 2）しており、perf-opt でも同じ効果が期待される。

### 修正内容（予定）

`## 前提条件` 節の直後（L22 後）に次を挿入:

```markdown
## 関連スキル・境界

本スキルは **動作は正しいが遅い** ケースに限定する。以下は別スキルへ委譲する。

| 状況 | 委譲先 |
|---|---|
| 誤動作・バグ修正（出力が誤っている、例外が出る） | `systematic-debugging` → `tdd` |
| 振る舞いを変えずコード構造のみ改善（計測不要の可読性改善） | `refactoring` |
| テストの信頼性検証（GREEN なのに偽陽性の疑い） | `test-coverage-guard` |
| 新規実装や interface 設計（既存コード不在） | `interface-first-design` → `tdd` |

**観測と変更の区別**: 本番環境での**読み取りのみの観測**（既存 APM / ログ / `EXPLAIN` 等）は前提条件下でも実施可能だが、本番への**変更適用**は必ずステージングでベースライン計測 → プロファイル → 1 変更ごとの検証を経てから行う（禁止事項「本番環境でのみ計測する」の射程）。
```
