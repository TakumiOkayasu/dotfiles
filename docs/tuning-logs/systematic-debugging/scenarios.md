# systematic-debugging シナリオカタログ

empirical-prompt-tuning でチューニングするための評価シナリオ。**iter 開始後は変更しない**。

- 対象スキル: `claude/skills/systematic-debugging/SKILL.md`
- description: 「バグやテスト失敗に遭遇した際に使用。修正前の4フェーズ根本原因分析を強制。」
- 収束目標: **連続3** イテレーション（重要スキル）

## 隣接スキルとの境界（iter 0 整合確認の焦点）

| スキル | 対比 |
|---|---|
| tdd | tdd = 修正**実装**、systematic-debugging = 修正**前**の原因分析。Phase 4 で tdd に引き継ぐ |
| failure-logging | failure-logging = 失敗**記録**、systematic-debugging = 失敗**分析** |
| test-coverage-guard | test-coverage-guard = GREEN 後のテスト信頼性検証、systematic-debugging = RED の原因分析 |

## Baseline シナリオ

### シナリオA（中央値: テスト失敗の原因特定）

**状況**:
Node.js プロジェクトで `user.service.test.ts` の `should_return_user_when_id_exists` が **直近の機能追加後に突然 FAIL** するようになった。エラーログは `TypeError: Cannot read properties of undefined (reading 'email')`。ユーザーは「直してほしい」と依頼。再現は `npm test -- user.service` で 100% 再現する。

**要件チェックリスト**:
1. [critical] **修正コードを書く前に 4 フェーズ（再現 / 境界トレース / 根本原因 / TDD 修正）を順に踏む**（SKILL.md L17）
2. [critical] **推測で修正しない**（一次ソース確認節。実ファイルを読む、ログ原文を引用する）
3. Phase 1: 再現手順を文書化する（100% 再現を明示）
4. Phase 2: 境界トレース（どの層 / どの時点でデータが壊れるか）を明示する
5. Phase 3: 「なぜ?」を最低2回繰り返して根本原因を言語化する
6. Phase 4: バグを再現するテスト（RED）を先に書いてから GREEN に進む
7. 対症療法（表面的な try-catch 追加 / `?.` でのお茶濁し）に走らない

### シナリオB（edge 1: 修正2回失敗後の再依頼）

**状況**:
前のセッションで同じバグに対し「null チェック追加」「デフォルト値設定」の 2 パッチを出したが **どちらも失敗**（別テストが壊れた / 本来の症状が再発）。ユーザーは「また落ちた、もう一度見て」と 3 回目の修正を依頼。修正履歴は会話に残っている。

**要件チェックリスト**:
1. [critical] **「3回以上の修正失敗 → アーキテクチャを疑う。ユーザーと相談。」を発動**（SKILL.md L75）
2. [critical] すぐ3回目のパッチを出さず、**ユーザーに構造的再検討を提案する**
3. 試した2回の修正内容とそれぞれの失敗結果をデバッグ記録テンプレートの「試したこと」節に整理して提示する
4. Phase 1 から再度やり直す（再現手順・最小再現ケースの見直し）
5. 境界トレース（Phase 2）を再実施し、前回の境界判定が間違っていた可能性を検討する
6. failure-logging との連携（同じ失敗を繰り返さない）を意識する

### シナリオC（edge 2: 再現手順が存在しない症状報告）

**状況**:
ユーザーから「なんか管理画面の保存ボタン押したとき、たまに保存されないときがある気がする。直して」とだけ報告。再現手順はユーザーも把握していない。エラーログの位置も不明。システムは Rails + React の社内ツール。

**要件チェックリスト**:
1. [critical] **再現手順が存在しないので Phase 1 で作成することを最優先にする**（SKILL.md L25「再現手順が存在しない場合はPhase 1で作成」）
2. [critical] **100% 再現可能になるまで修正提案をしない**（SKILL.md L40「再現できなければ修正提案禁止」）
3. 症状の正確な記録（いつ / どの操作 / どんな条件 / ブラウザ・ネットワーク状態）をユーザーに確認する
4. 最小再現ケース構築の計画を提示する（操作手順の確定 → 環境情報収集 → ログ収集範囲の特定）
5. 「たまに」の頻度・条件を切り分ける問いをユーザーに投げる
6. 修正方針を先走って提示しない（対症療法禁止）

## Hold-out シナリオ（収束判定時のみ使用）

### シナリオD（本番でのみ再現するバグ）

**状況**:
本番環境でのみ発生する間欠障害（レート 1%）。staging では再現不能。ログには `ECONNRESET` が散発的に出ているが他サービスでも出るノイズ混じり。ユーザーは「本番で 1% 落ちるから急いで直して」と依頼。

**要件チェックリスト**:
1. [critical] **100% 再現できない段階で修正提案を出さない**（SKILL.md L40）
2. [critical] **エラーメッセージを原文確認せず対応しない**（SKILL.md L101）。ログ原文をユーザーに提出依頼する
3. Phase 1 として、本番で再現する条件（時刻・ユーザー属性・リクエスト内容）の統計収集をまず提案する
4. 環境情報の収集（本番と staging の差分）を明示する
5. 対症療法（リトライ追加で隠蔽）に逃げず、根本原因特定を優先する
6. 緊急度が高い場合のトレードオフ（一時的緩和策 vs 根本対応）をユーザーに判断させる

## 運用メモ

- シナリオ B は「修正済パッチを見て軌道修正できるか」の観点。同一 subagent 使い回しは empirical-prompt-tuning で禁止だが、シナリオ文脈内で 2 回の修正履歴を明示すれば評価可能
- シナリオ C は tdd との区別が最も試される（テストがないので「テスト書いて」に誘導されるリスク）
- シナリオ D は hold-out として、**再現不能 = 修正禁止** の鉄則を守れるかを試す
