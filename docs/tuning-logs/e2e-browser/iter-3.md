### シナリオ C の外れ値について

C の tool_uses=4 / duration=126s は **file write 拒否による subagent 側試行錯誤**（冒頭「ファイル書き込みが拒否されたため、生成物を本文中に提示する方式に切り替えます」）。
- 応答品質: 精度 100%（iter 2 の 93.75% から +6.25pt 昇格）で正常以上
- tool_uses 偏り: C 単体で他シナリオ比 4 倍 = empirical L67 の「3-5 倍」閾値に触れるが、構造的欠陥でなく **環境側（書込拒否）の一過性事象**
- refactoring iter 2 シナリオC（423s）/ interface-first-design iter 1 B・C（1370s）と同種の外れ値パターン、**除外後で飽和条件判定** を採用（empirical 実績踏襲）

### 境界節追加の実地効果観察

- **シナリオ B**: 「本スキルは再現と修正提案まで。アプリ側の根因分析は `systematic-debugging` へ委譲すべき領域。ただし E2E テストコード/fixture 側の対応は本スキルで完結可能」と **新節の趣旨を直接引用**。iter 2 で自発改善だったものが iter 3 で構造化された境界宣言に格上げ
- **シナリオ C**: docker-compose YAML を具体化して部分的→○（iter 2 93.75% → iter 3 100%）。境界節は直接引用されないが、新節で「本スキルが扱う範囲」が明示されたことで「本スキル範囲内は具体化する」という方向性が強化
- **シナリオ A**: 新節への言及なし。元々 iter 2 で 100% 達成のため差が観察しにくい（天井効果）
