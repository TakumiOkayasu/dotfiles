## iter 4 テーマ選定

### 候補比較

| テーマ | 根拠 | 修正コスト | 波及期待 |
|:-:|---|:-:|:-:|
| **null vs Ok/Error ポリシー整理** | IFD-3-C-2 = **3 iter 継続の最古残存**。L108「戻り値は Ok/Error の 2 値」と Anti-pattern 1 の `User \| null` が一見不整合。subagent が毎回「読取=null、副作用=Ok/Error」と裁量解釈 | 小（L108 に 1 行補足）| 中（読取/副作用の書き分けを明文化、全シナリオ波及） |
| refactoring 境界の逆方向委譲明記 | iter 0 IFD-0-3 から 3 iter 継続、subagent が自力判断済 | 小（委譲先節 3-5 行）| 小（subagent 自制成功で実害なし）|
| `[要確認]` 集約フォーマット明示化 | iter 3 で 3 subagent 揃ってほぼ同一だが形式に揺れ | 中（出力形式テンプレ拡張）| 小 |

### 選定: **null vs Ok/Error ポリシー整理**

**理由**:
1. 3 iter 継続の**最古残存** = 構造的に潰すべき
2. L108 の文言と Anti-pattern 1 の例が subagent を都度裁量解釈させる = 明文化で解消
3. tdd iter 3 の A-2' の例外節末尾追記パターンと同じ構造（1 行追記で解消期待）
4. 読取系 (`T | null`) と副作用系 (`Ok | Error`) の書き分けは interface-first-design の核（Anti-pattern 1 の `findByEmail(email) -> User | null` が既に模範例）

### 修正案

Step 2「変換ルール」L108 を以下に置換:

```markdown
- 戻り値は用途で書き分け: 読取系 (`find` / `read` 等、副作用なし) は `T | null` で not-found を明示、副作用系 (`write` / `charge` / `delete` 等) は `Ok | Error` で成功/失敗を明示する
```
