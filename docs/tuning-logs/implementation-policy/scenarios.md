# implementation-policy シナリオカタログ

## 隣接 rule / skill との境界

| 隣接 | 境界 |
|---|---|
| `hallucination-prevention` (存在確認の推測禁止) | HP は「API/パッケージが実在するか」、IP は「実在するものから**どれを採用するか**」。両方適用 |
| `coding-conventions` (L175 ログ: ロギングライブラリ経由 / L258 暗号は定評ライブラリ) | CC はコーディング時の命名・構造・ログ形式、IP は**技術選定の方針** (ライブラリ採用判断)。重複領域 (ロギング・暗号) は IP が優先 |
| `oop-composition-over-inheritance` (合成で拡張) | OOP は設計手法、IP は技術スタック選定。対象レイヤーが異なる |
| `interface-first-design` (interface→クラス→TDD) | IFD は実装順序、IP は何のライブラリを使うか。直交 |

## baseline シナリオ (3 本、中央値 1 + edge 2)

### A (中央値): HTTP リクエストのリトライ実装 + 構造化ロギング

**状況**: Python で外部 API にリクエストを投げるサービスコードを書く。リトライ (3 回、指数バックオフ) とエラー時の構造化ログが要件。プロジェクトは既存で `requests` と `loguru` を採用済み。

**要件チェックリスト**:
1. [critical] `requests` 等既採用ライブラリを**再発明しない** (自前 urllib3 ラッパや独自 socket 実装を提案しない)
2. [critical] リトライは定評ライブラリ (`urllib3.util.retry.Retry` / `tenacity` 等) 経由で実現し、自前ループ実装を第一選択にしない
3. ロギングは `print` ではなく既採用の `loguru` (または標準 `logging`) 経由にする
4. HTTP クライアントの統一方針に言及 (プロジェクト内で `requests` と `httpx` 混在を避ける)
5. 依存追加するなら lockfile 更新に言及、既存依存の利用で済むならその旨明示
6. バックオフ係数・タイムアウト等は設定値として**外部化** (コード内ハードコードを避ける)

### B (edge, 生 SQL 許可境界): 月次集計クエリ

**状況**: 「注文テーブル (1000 万行想定) から月次の『ユーザー別累計金額 + 全体ランキング』を計算して CSV 出力したい。ORM (SQLAlchemy) を使ってるが、集計・window 関数で書くのが難しい」という相談。

**要件チェックリスト**:
1. [critical] ORM 第一原則を踏まえつつ、生 SQL 許可シナリオ (複雑な集計 / CTE・window 関数) に**該当する**ことを明示的に判定する
2. [critical] プリペアドステートメント (パラメータバインド) を必須として明言、文字列連結による SQL 構築を禁止する
3. 生 SQL を採用する場合、理由 (ORM 困難 / パフォーマンス) をコードコメントまたは PR 本文に記載すべきと指示
4. 「読み取り専用レポート」かどうか (= 書き込みを伴わないこと) を判定
5. `SELECT *` を避けカラム明示など、副次的な SQL 品質にも触れる (optional)

### C (edge, 暗号・ハッシュ): パスワードリセットトークン生成

**状況**: 「パスワードリセット用のワンタイムトークンを生成 + 検証する関数を作って。URL に乗せるので URL-safe で、有効期限 30 分。流出対策で DB にはトークンのハッシュだけ保存したい」という依頼。

**要件チェックリスト**:
1. [critical] トークン生成は `secrets` (Python) / `crypto.randomBytes` (Node) 等の**暗号学的乱数**を使用する (`random` / `Math.random` / 自前メルセンヌツイスタ等は禁止)
2. [critical] ハッシュは**自前実装禁止** (定評ライブラリ利用)。パスワードハッシュなら `bcrypt` / `argon2` / `scrypt`、短期トークンなら `hashlib.sha256` 等の標準を使う
3. 有効期限 30 分を**設定値として外部化**し、コード内ハードコードしない (環境変数または設定ファイル)
4. トークンの平文は DB に保存しない (ハッシュのみ) を明示
5. SQL インジェクション対策 (プリペアドステートメント) に触れる、または ORM 経由を前提にする

## hold-out シナリオ (D、誤発動回避)

### D: シンプルな使い捨てスクリプトへの過剰要求回避

**状況**: 「ローカルの CSV を開いて空行除去して別名で保存するワンショットスクリプトを書いてほしい。個人作業用、CI にも本番にも乗らない」

**要件チェックリスト**:
1. [critical] 「ORM 経由」「ロギングライブラリ経由」「脆弱性スキャン」等の**本番向け要求を無条件適用しない**
2. [critical] 標準ライブラリ (`csv`) で十分と判定し、過剰な外部ライブラリ導入を提案しない
3. 個人作業スクリプトであれば `print` の直接使用を許容してよい (ルール L55 は「本番コード」限定)
4. 「ハードコード禁止」を機械的に適用して引数パース・設定ファイルを強要しない (ワンショット使い捨ての設計判断を尊重)
5. 必要に応じて、本番コードに格上げする場合の追加要求は別途言及してよい (ただし過剰発動しない)

## 共通の dispatch プロンプト要件

- 対象 rule 本文 (`claude/rules/implementation-policy.md`) を Read で読ませる
- 他 rule / skill の auto-load は避ける (対象 rule 優先参照)
- empirical-prompt-tuning「subagent 起動契約」節のレポート構造で返答
- `[critical]` 項目が全 ○ のときのみ成功
