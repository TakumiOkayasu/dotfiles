# tdd シナリオカタログ

empirical-prompt-tuning でチューニングするための評価シナリオ。**iter 開始後は変更しない**。

- 対象スキル: `claude/skills/tdd/SKILL.md`
- description: 「機能実装やバグ修正でテストを書く・変更する作業に使用。RED-GREEN-REFACTORサイクルを適用する。」
- 収束目標: **連続3** イテレーション（重要スキル）

## Baseline シナリオ

### シナリオA（中央値: 純粋関数の新規実装）

**状況**:
既存 TypeScript プロジェクトで、`isValidISODate(input: string): boolean` という日付文字列バリデータを新規実装してほしいと依頼された。プロジェクトには Vitest が導入済みで `npm test` が動く。依頼内容は「ISO 8601 形式（`YYYY-MM-DD`）の文字列なら true、それ以外（空文字、不正形式、存在しない日付 `2026-02-30` 等）は false を返す」。TDD で進めてほしいとユーザーから明示された。

**要件チェックリスト**:
1. [critical] **実装コードを書く前にテストリストを自然言語で提示する**（SKILL.md ステップ2）
2. [critical] **テスト→実行→FAIL 確認→実装** の順序を守り、RED 確認を出力で示す
3. [critical] **1 サイクル = 1 テストケース**。複数テストを同時に書いて一気に実装しない
4. テストリストに境界値（空文字、存在しない日付、typo された月など）を明示的に含める
5. プロジェクト検出（ステップ0: テストフレーム / 配置規約 / 実行コマンド）を冒頭で行う
6. GREEN 後に REFACTOR 判断（重複 / 命名 / 責務）を明示する
7. 弱いアサーション（`toBeDefined()` 単独など）を使わない

### シナリオB（edge 1: レガシーコードへの TDD 導入）

**状況**:
既存 Python プロジェクトで、`services/order_total.py` の `calculate_total(items, coupon_code)` 関数の仕様を変更してほしいと依頼された。この関数は**テストが一切ない**。約 80 行で、内部で DB アクセスもあり、現在の振る舞いがドキュメント化されていない。ユーザーは「TDD 的に安全に進めてほしい」と依頼。

**要件チェックリスト**:
1. [critical] **いきなり新機能のテストを書かず、特性テスト（characterization test）で現状を記録する段階**を踏む（SKILL.md ステップ4）
2. [critical] **既存コードの振る舞いを「正しいかは問わず」そのまま記録**する方針を明示し、期待値に確信がない箇所は `// TODO: 仕様確認後に修正` コメントを付ける
3. 特性テストを通常テストから分離する（`describe("CHARACTERIZATION: ...")` / タグ / ファイル分離のいずれか）
4. テスタビリティ判断（DB アクセス密結合 = テスタブルでない）を明示し、リファクタ必要性を指摘
5. 判断マトリクス（仕様×テスタビリティ）を参照して行動を決める
6. ユーザーに「仕様の確度」を確認する問いを投げる

### シナリオC（edge 2: 曖昧仕様での適用判断）

**状況**:
ユーザーから「チャット履歴の保存機能を **なんとなくこんな感じで** 作ってほしい。詳細は作りながら決める」と依頼された。インターフェースも型定義も未定。関連する設計資料もない。ユーザーはテスト駆動に慣れており「TDD で進められるならそうしたい」と言っている。

**要件チェックリスト**:
1. [critical] **AI 独断で「探索的」と判定して実装先行に走らない**。ユーザーに明示的に申告を求める（SKILL.md L93「『探索的』は常にユーザー申告制」）
2. [critical] 仕様確度（確定 / 方針のみ / 探索的 / 不明）の分類を提示し、今回がどこに該当するかをユーザーに確認する
3. 「方針のみ」の場合の推奨行動（統合テスト先行 + 詳細は実装しながら追加）を判断マトリクスから提示する
4. 「探索的」の場合の2択（実装先行 / 仕様を先に固める）をユーザーに選ばせる
5. テストリスト作成を強行しない（仕様が曖昧な段階でリストを作ると後で破綻する）

## Hold-out シナリオ（収束判定時のみ使用）

### シナリオD（既存テストの期待値が疑わしい場合）

**状況**:
既存 Go プロジェクトで、`user_service_test.go` に `TestCreateUser_ReturnsErrorForEmptyEmail` というテストがあり PASS している。だがテスト本体を読むと期待値が `errors.New("invalid")` となっており、`errors.New("email required")` が正しいのでは、とユーザーが疑問を持った。ユーザーは「TDD の流れで直してよい？」と聞いてきた。

**要件チェックリスト**:
1. [critical] **ユーザー承認なしに既存テストの期待値を書き換えない**（SKILL.md 禁止事項「既存テストをユーザー確認なしに変更・削除する」）
2. [critical] 「振る舞いが変わっていないのにアサーションの期待値を変える」ことが禁止されている原則を明示する
3. 期待値変更の正当な手順（仕様確認 → ユーザーに理由と新旧を提示 → 承認後に変更）を案内する
4. 期待値変更テンプレート（「テスト[名前]の期待値を[旧]→[新]に変更してよいですか? 理由: [理由]」）を使う
5. 「テストは仕様」原則（SKILL.md 鉄則2）を根拠として示す

## 運用メモ

- 各シナリオは現実の使用頻度で並べている（A > B > C）
- `[critical]` が全て ○ のシナリオのみ成功（○）判定。1つでも × or 部分的 → 失敗（×）
- 精度 = 全要件の達成率（○=1.0, 部分的=0.5, ×=0）
- シナリオ B/C は境界スキル（systematic-debugging / interface-first-design / consultation）との判別も試す
