# Pattern Thinking Skill

## トリガー

- 新しい機能の設計時
- 依存性管理の方針決定時
- 状態管理の設計時
- 既存コードのリファクタリング時
- 「どのパターンを使うべきか」という判断が必要な時

## 目的

コード設計において「よくあるパターン」に安易に飛びつかず、問題の本質に合った
パターンを選択する。必要に応じて独自アプローチも積極的に提案する。

## 思考プロセス

### Phase 1: 問題の特性分析

実装に入る前に、以下を明確にする:

**変化の軸**

- 何が頻繁に変わる?
- 何は安定している?
- 変更の頻度と影響範囲は?

**依存関係**

- 何が何に依存している?
- 循環依存はある?
- 依存の方向は適切か?

**制約**

- メモリ制約(組み込み: KB単位、サーバー: GB単位)
- CPU/パフォーマンス要件
- リアルタイム性の要求
- 可読性・保守性の優先度
- チームの経験・スキルセット

**寿命**

- 使い捨てのプロトタイプか?
- 長期保守が必要か?
- ライブラリとして公開するか?
- 他プロジェクトで再利用するか?

### Phase 2: パターンスペクトラムの提示

**必ず3段階以上の選択肢を提示する:**

| レベル | 説明 | 特徴 |
|--------|------|------|
| 🟢 Conservative | 広く知られた標準パターン | 低リスク、高い可読性、豊富なドキュメント |
| 🟡 Pragmatic | 状況に応じた応用パターン | バランス型、学習コストと効果のトレードオフ |
| 🔴 Experimental | 独自/先進的アプローチ | 高効果の可能性、学習コスト高、情報少ない |

**各レベルの採用基準:**

🟢 **Conservative(保守的)**

- 採用条件: チーム全員が理解できる、短期プロジェクト、プロトタイプ
- リスク: 問題に最適化されていない可能性
- 例: Constructor Injection(手動)、State Pattern(GoF)、Repository Pattern

🟡 **Pragmatic(実用的)**

- 採用条件: 特定の問題に対する効果的な解決策が必要、中規模以上のプロジェクト
- リスク: チームの経験値に依存、過剰適用の危険
- 例: DIコンテナ、CQRS、Hexagonal Architecture

🔴 **Experimental(実験的)**

- 採用条件: 問題に対する最適解の可能性、技術的挑戦、差別化が必要
- リスク: 情報が少ない、メンテナンス負荷、採用ハードル
- 例: Context Pattern(組み込み向け)、ECS、Actor Model

### Phase 3: トレードオフの明示

各パターンについて、以下を必ず説明:

```
【パターン名】

得られるもの:
- このパターンで解決される問題

失うもの:
- 複雑性の増加
- パフォーマンスへの影響
- 学習コスト

適用条件:
- どんな状況で威力を発揮するか

アンチパターン:
- このパターンが害になるケース
```

### Phase 4: 推奨の提示

```
【推奨】{レベル}: {パターン名}

理由:
1. {具体的な理由1}
2. {具体的な理由2}
3. {具体的な理由3}

ただし、{条件}の場合は{別パターン}も検討価値あり。
```

## NEVER(絶対に避けること)

- ❌ 単一パターンのみの提示
- ❌ 理由なき「とりあえずこれ」
- ❌ トレードオフの説明なき推奨
- ❌ 「一般的にはこうします」という思考停止
- ❌ Conservativeレベルのみの提案(必ずPragmatic以上も検討)
- ❌ プロジェクトの制約を無視したパターン適用
