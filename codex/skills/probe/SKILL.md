仮説を立て、計測用ログを実コードへ挿入し、実際に動かして得たログからボトルネックの位置を洗い出し、そこだけを最適化する手技。プロファイラの自動計測では粒度が足りない/環境的に使えないときに、自分で計装点を置いて当たりを付ける。

## トリガー条件

いずれか該当で適用する。

- どこが遅いのか位置が分からず、当たりを付けて計りたい
- 計測用ログを実コードへ仕込んで実行時の時間内訳を取りたい
- 仮説を立ててボトルネック位置を絞り込みたい
- プロファイラが導入できない/出力粒度が粗くて関数内の特定区間を計れない
- 複数の遅延要因候補があり、並行して計装し一度の実行で切り分けたい

## 前提条件

- 対象コードを編集でき、実際に動かして再現できること
- 再現手順が存在すること (なければ Phase 1 で作る)
- 計測結果を比較するベースラインが取れること

## 関連スキルとの境界

性能まわりは複数スキルが隣接する。本スキルは **計装ログを自分で挿入してボトルネック位置を特定する手技** に限定する。

| 状況 | 委譲先 |
| --- | --- |
| 何を最適化すべきかの判断/層横断の案出し/相手の最適化提案の妥当性検証 | `optimize` |
| プロファイラ/APM/負荷テストでの計測全般、最適化サイクルとレポート出力 | `measure` |
| 動作が誤っている (出力が誤り/例外) の根本原因分析 | `systematic-debugging` |
| 振る舞いを変えずコード構造のみ改善 (計測不要) | `refactoring` |

使い分けの軸:

- 速くする「位置」がプロファイラで自動的に分かるなら `measure`。プロファイラで届かない区間を **自前のログ挿入で特定する** のが本スキル
- 速くする「何を/どの層で」を考えるのは `optimize`。本スキルは位置特定後の最適化までを一気通貫で扱うが、層を跨ぐ重い案の判断が要るときは `optimize` へ寄せる
- 仮説駆動 + subagent 並列の構造は `systematic-debugging` Phase 3.5 と同型。対象が誤動作なら `systematic-debugging`、動作は正しいが遅いなら本スキル

## 鉄則

**推測でホットパスを当てにいかない。仮説 → 計装 → 実行 → ログで検証 → 最適化。**

- 計装ログは観測者効果を持つ。挿入自体が遅延を生む点を常に意識する (後述)
- 1 度の最適化につき計測を 1 回はさむ。効果がなければ即リバートする
- ログで裏付けの取れていない箇所は最適化しない

## 手順

### Phase 1: 再現とベースライン

最適化対象の指標を 1 つ決める (レイテンシ/スループット/メモリのいずれか)。

```
- [ ] 遅いと疑われるコードパス/エンドポイントを特定する
- [ ] 再現手順を文書化する (入力/操作/環境)
- [ ] ベースラインを複数回計測して記録する (1 回計測は信用しない)
- [ ] 目標値を決める (この値を下回れば完了)
```

ウォームアップ後に複数回計測し、中央値とテイル (p99/max) を記録する。平均だけ見ない。

### Phase 2: 仮説を立てる

ログを挿す前に、どこが支配的かの仮説を最低 2 つ書き下す。仮説には計装で検証できる具体性を持たせる。

```
仮説の型:
  - 「区間 A (DB アクセス) が全体の N% を占める」
  - 「ループ X が想定の M 倍呼ばれている」
  - 「シリアライズが入力サイズに対し非線形に伸びる」
```

各仮説に「どこへログを挿せば真偽が判定できるか」を対にする。判定できない仮説は具体化し直す。

### Phase 3: 計測用ログを挿入する

仮説を検証する区間の前後へ計装点を置く。原則:

- 入口/出口で経過時間を出す。区間を入れ子にして内訳を取れるようにする
- 計装点に一意なラベルと相関 ID を付け、後でログを機械集計できる形にする
- ホットループ内に重いログを置かない。観測者効果で対象自体が遅くなる。集計は呼び出し回数と累積時間に留め、1 反復ごとの出力は避ける
- ロガー経由の構造化ログ (キー/バリュー) で出す。`print` / `console.log` の直接埋め込みは使い捨て調査時のみとし、残さない
- 計装は一時的な変更として独立コミット/スタッシュにまとめ、撤去を容易にする

観測者効果の確認: 計装ありとなしでベースラインが大きく変わる場合、ログ自体がボトルネックを作っている。サンプリング (N 回に 1 回) か、より粗い区間へ計装点を移す。

### Phase 3.5: 並列計装 (subagent dispatch)

仮説が複数、または計装対象パスが複数に分かれる場合は subagent へ分散する。dispatch 形式/並列起動の作法/種別選択は `${HOME}/.codex/SUBAGENTS.md` を参照。

起動条件 (いずれか):

- 仮説が 2 つ以上あり、それぞれ別の区間/ファイルへ計装する
- 計装対象が 3 ファイル以上、または 3 層以上 (API/Service/DB 等) にまたがる
- 同一実行ログに対し複数観点 (時間内訳/呼び出し回数/メモリ) で並行集計したい

本スキル固有の dispatch 内容: 各 subagent に「検証する仮説 1 つ + 計装すべき区間 + ログ出力形式」を渡し、「担当区間のみへ計装し、他仮説の区間には触れるな」と制約する。subagent 種別はコード探索中心なら `Explore`、横断的調査なら `general-purpose`。

集約: 各 subagent の計装差分を親が統合し、1 度の実行で全区間のログを取得する。ログを仮説ごとに突き合わせ、累積時間/呼び出し回数で支配区間を確定する。**どの仮説のログも支配的でなければ Phase 2 (仮説) へ戻る** (当たりが外れている)。

起動しないケース: 仮説が 1 つに絞れている/計装が 1 区間で済む/局所的で並列のオーバーヘッドが上回る場合。

### Phase 4: 最適化

特定した支配区間だけを最適化する。軽い案から当てる (入力を絞る → 実行回数を減らす → アルゴリズム変更 の順)。層を跨ぐ重い案 (キャッシュ層追加/並列化/言語切替) の判断が要るときは `optimize` を併用する。

- 1 変更ごとに計装ログ付きで再実行し、効果を数値で確認する
- 効果がなければ即リバートする。複数変更を同時に当てない (原因を特定できなくなる)
- ベースラインと同一条件で再計測し、p50/p99 の before/after を記録する (テイルの悪化も見る)
- 完了前に計装ログをすべて撤去する。本番コードに残さない

## アンチパターン

- 計装せず推測で「ここが遅そう」と最適化に入る
- 計装ありのログを本番コードに残す
- ホットループ内に重いログを埋め、観測者効果で偽の支配区間を作る
- 1 回計測で判断する (ウォームアップ前/外れ値を真に受ける)
- ログで支配的と確認できていない箇所を最適化する
- 複数の最適化を同時に当て、効果の原因を特定できなくする
- 平均だけ見てテイル悪化を見逃す
- プロファイラで自動的に位置が分かるのに手計装で時間を浪費する (→ `measure`)

## 一次ソース確認

- コード確認: 実ファイルを読んで計装点を決める (推測で行番号を当てない)
- ログ: 実行して得た原文ログを引用し、推測値で埋めない
- 計測値: ベースラインと最適化後を同一条件で取得した実測値のみを報告する
