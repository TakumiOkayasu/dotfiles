# OOP設計原則: インターフェースによる抽象化と合成

## 基本原則

### 抽象化の目的
- 実装の詳細を隠蔽し、契約(インターフェース)のみを公開する
- 利用側は実装に依存せず、インターフェースにのみ依存する
- 各実装は他の実装を知る必要がない

### 合成による拡張性
- 小さく独立した機能単位を組み合わせて複雑な機能を実現する
- 機能の追加・変更時に既存コードへの影響を最小化する
- 組み合わせる順序や構成を外部から制御可能にする

## 設計の判断基準

### ❌ 悪い設計の兆候
- **パラメータを増やすだけの設計**
  - 新機能のたびに引数やメンバ変数を追加
  - 条件分岐が増え続ける
  - 実装が肥大化しているだけで、機能が増えていない

- **既存コードの変更が必要**
  - 新機能追加時に既存クラスの処理を追加・変更
  - 機能の組み合わせごとにクラスや分岐が必要
  
- **責務の不明確さ**
  - 一つのクラスが複数の責務を抱えている

### ✅ 良い設計の兆候
- **新しい実装クラスを追加するだけで機能拡張できる**
  - 既存コードは変更不要
  
- **インスタンス化時の組み合わせで挙動を制御できる**
  - 合成の順序を変えるだけで異なる挙動を実現
  
- **各クラスは単一の責務のみを持つ**
  - インターフェースは薄く保つ(必要最小限のメソッドのみ)

## 実装のポイント

1. **インターフェースに依存する**
   - 具体的な実装クラスではなく、インターフェースに依存
   - 各実装クラスはインターフェース以外に依存しない

2. **内部実装を隠蔽する**
   - バッファ管理、最適化などは完全に隠蔽
   - 外部から見えるのはインターフェースだけ

3. **外部から合成する**
   - 合成する際は外部でインスタンス化
   - 依存性を注入する(DI)

## 継承を採用してよい場面

以下のケースでは継承を採用してよい。判断基準は「悪い設計の兆候」(パラメータ増・条件分岐増・責務肥大) に該当しないこと:

- **フレームワーク/ランタイムが継承を要求する基底**: React `Component`, Django `View`, Android `Activity` 等
- **is-a 関係が明確なドメイン階層**: `Enemy is a GameObject`、値オブジェクト階層など
- **Mixin (多重継承形式の合成)**: `LoginRequiredMixin` 等、機能単位を組み合わせる継承構文

**継承深度の目安**: 2 段まで。それ以上は「責務の不明確さ」のリスクが上がるため合成を検討する。機能差分 (能力・振る舞い) は継承ではなく合成 (コンストラクタ注入) で注入する。

## 適用範囲

この原則は以下のすべてに適用可能:

- **組み込み開発**: Context パターン(Android Application Context)
- **宣言型UI**: Widget/Component の合成(Flutter, React, SwiftUI)
- **バックエンド**: Middleware, Repository, Dependency Injection
- **データ処理**: Stream, Pipeline, Chain of Responsibility

## 具体例の参照

各環境での具体的な実装例は以下を参照:
- 組み込み: Context パターンによるメモリ制約への対応
- Web/Mobile: 宣言型UIでの合成の可視化
- Backend: Middleware/DI による横断的関心事の分離

---

**原則**: 特定の処理(ストリーム、フィルタ、変換など)に限らず、OOP における拡張性の高い設計全般に適用できる指標となる。
