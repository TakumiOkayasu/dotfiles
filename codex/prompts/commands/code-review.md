# コードレビュー

直近の変更をレビューする。

## 引数

`$ARGUMENTS` にレビュー対象を指定（省略時は直近の変更）

## 入力

| 入力元 | 内容 |
|--------|------|
| `$ARGUMENTS` | ブランチ名・コミットハッシュ・ファイルパス等（省略可） |
| `git diff` | ステージ済み＋未ステージの差分 |
| `AGENTS.md` / `codex/rules/` | プロジェクト規約 |

## 出力

| 出力項目 | 内容 |
|----------|------|
| 判定ヘッダー | `BLOCK` / `WARN` / `PASS` |
| サマリー表 | Critical / Warning / Suggestion 件数 |
| 各指摘 | 重要度・ファイル:行・問題・現状コード・修正案・理由 |

## 鉄則

**全指摘に修正コードを添える。修正案なき指摘は指摘ではない。**

---

## レビュー手順

### Step 1: 差分取得

```bash
# $ARGUMENTS が指定されている場合はそれを使用
# 省略時は以下を順に試行:
# 1. git diff HEAD        （ステージ済み＋未ステージの変更）
# 2. git diff HEAD~1      （直近コミットの変更）
```

### Step 2: 全体把握

1. 変更の目的・スコープを理解する
2. 影響範囲を特定する
3. 変更ファイルの import / 依存グラフを確認する

### Step 3: プロジェクトルール展開（必須・スキップ禁止）

**このステップを飛ばしてはならない。**

1. `AGENTS.md` を読み、記載された規約・禁止事項を**全て列挙**する
2. `codex/rules/` 内の全ルールファイルを読む
3. `codex/rules/` 内の全ルールファイルを読む
4. 読んだ各ルールに対して、**今回の差分で違反しうる具体的パターン**を列挙する
   - ルールが存在しない場合はそのルールの展開をスキップする
5. 列挙したパターンを Step 4 のカテゴリ 10「プロジェクト整合性」に追加する

**展開例（hierarchical-architecture）**:

```text
- 依存方向: A→B の import があるが、B→A の逆依存はないか
- 命名: *Manager, *Provider, *Accessor の規則に従っているか
- IF設計: 1インターフェース1責務か。Readable+Writable 混在はないか
- 合成: 2階層超の継承はないか。コンストラクタ注入で合成しているか
- 入力抽象化: Raw→Calibrated→Intent の階層を守っているか
```

**展開例（hallucination-prevention）**:

```text
- 使用API/パッケージは実在するか（公式リファレンスで確認）
- 引数の数・型・順序は正しいか
- 非推奨APIを使っていないか
- ユーザー環境のバージョンで利用可能か
```

**スキルの活用検査も必須**:

```text
- プロジェクトの skills/ に定義された手順を活用しているか
- test-driven-development スキルがあるなら RED-GREEN-REFACTOR を守っているか
- systematic-debugging スキルがあるなら推測修正をしていないか
- premise-questioning スキルがあるなら大規模変更で方針検証を経たか
- feature-pruning スキルがあるなら機能粒度の要否検証を経たか
```

**方針検証観点 (戦略 → 戦術) の追加検査**:

レビュー対象差分が以下に該当する場合、`premise-questioning` / `feature-pruning` の **発動跡**を確認する:

| 検査対象 | 発動必須条件 | スキル参照先 |
|----------|-------------|-------------|
| 戦略 (方針自体) | 100 行以上の変更 / 外部依存追加・削除 / DB スキーマ・公開 API I/F 変更 / バグ修正で根本原因に手を入れる | `codex/skills/premise-questioning/SKILL.md` |
| 戦術 (機能粒度) | UI 機能リスト 5 個以上 / API エンドポイント複数新設 / DB テーブル 5 列以上新設 / 既存機能の削減 | `codex/skills/feature-pruning/SKILL.md` |

**発動跡の判定基準** (いずれか 1 つ以上を満たせば「発動跡あり」と判定):

| 確認対象 | 発動跡と認める記述 |
|----------|------------------|
| PR 本文 | `premise-questioning` / `feature-pruning` / `方針検証` / `✅ 採用` / `skipped (理由: ...)` のいずれかを含む |
| コミットメッセージ | 同上 |
| `codex/progress.md` の判断ログ | 当該方針の検証結果 (採用 / 撤回 / 修正必要 / skipped) が記録されている |
| 差分中のコメント | 該当箇所に `// premise-questioning: ...` / `# feature-pruning: ...` 等の明示的タグがある |

上記いずれの跡も見当たらない場合、または発動跡があっても結論ラベル (✅ / 🟡 / 🔴 / skipped) が読み取れない場合は **Critical** として指摘する。

該当条件に当てはまるが発動跡が見当たらない場合の指摘テンプレ:

```text
[Critical] 方針検証スキップ
- 該当条件: <100 行以上の変更 / 外部依存追加 / 等>
- 必要 skill: premise-questioning (戦略) / feature-pruning (戦術)
- 確認対象: PR 本文 / コミットメッセージ / codex/progress.md / 差分内コメント
- 対応: マージ前に該当 skill のワークフローを実施し、結果 (✅ 採用 / skipped 等) を PR 本文に追記
```

### Step 4: カテゴリ別検査

下記チェックリスト（11カテゴリ）を**全カテゴリ順に検査**する。
Step 3 で展開したプロジェクト固有パターンをカテゴリ 10 に統合して検査する。

### Step 5: 自己検証

自己検証プロトコル（8項目）に従い、全指摘を検証する。

### Step 6: 出力

出力形式に従い、マージ判定とともに結果を報告する。

## チェックリスト

### 1. 正確性

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| 境界値エラー | off-by-one、空配列、nil/null/undefined | Critical |
| 型不一致 | 暗黙の型変換、any型の乱用、union型の未検査 | Critical |
| 競合状態 | 共有リソースの非排他アクセス、TOCTOU | Critical |
| ロジックエラー | 条件分岐の抜け漏れ、短絡評価の誤用、演算子の優先順位 | Critical |
| null安全性 | nullable な値の未チェックアクセス、Optional の不適切な扱い | Critical |

### 2. アーキテクチャ・依存関係

`hierarchical-architecture` 等のアーキテクチャ系ルールが存在する場合のみ検査する。該当ルールが存在しない場合はスキップする。

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| 依存方向違反 | 依存がピラミッド型（上→下のみ）か。下位→上位依存の検出 | Critical |
| 横参照 | 同一レイヤー間の直接参照がないか | Critical |
| 段階飛ばし | 上位が下位を飛び越えてアクセスしていないか | Critical |
| 上位による内部操作 | 上位が下位の内部状態を直接操作していないか（指示のみ許可） | Warning |
| 公平性違反 | 同レベルに異なる抽象化情報を伝達していないか | Warning |
| インターフェース責務混在 | 単一IFに複数責務（入出力混在、Readable+Writable等）がないか | Warning |
| 具象依存 | インターフェースではなく具象クラスに直接依存していないか | Warning |
| 深い継承 | 2階層超の継承チェーン。合成に置き換えるべき | Warning |

### 3. 設計原則（SOLID / DRY / KISS / YAGNI）

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| 単一責任違反 | 1関数/クラスが複数の理由で変更される | Warning |
| 開放閉鎖違反 | 新機能追加時に既存コードの修正が必要になる設計 | Warning |
| リスコフ置換違反 | サブタイプが親型の契約（事前条件・事後条件）を破っている | Critical |
| インターフェース分離違反 | クライアントが使わないメソッドへの依存を強制 | Warning |
| 依存性逆転違反 | 上位モジュールが下位の具象に依存 | Warning |
| コード重複（DRY） | 同一ロジックの3箇所以上の記述 | Warning |
| 不要な複雑さ（KISS） | より単純な解決策が存在するのに複雑な実装 | Warning |
| 投機的汎用化（YAGNI） | 現在不要な機能・設定可能性の追加 | Warning |
| 関心の混在 | ビジネスロジックとI/O、表示とデータ処理の混在 | Warning |
| 設定値ハードコード | マジックナンバー、設定値の直書き。2回以上使用するリテラルは定数化必須 | Warning |

### 4. エラーハンドリング

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| エラー握り潰し | 空の catch ブロック、エラー無視 | Critical |
| 汎用キャッチ | `catch (Exception e)` で全例外を捕捉 | Warning |
| fail-fast 欠如 | 不正な状態の早期検出・報告がない | Warning |
| 例外の制御フロー利用 | 正常系のフロー制御に例外を使用 | Warning |
| エラー種別の未区別 | 業務エラー/システムエラー/プログラムエラーの混同 | Warning |
| リカバリ不適切 | リトライすべきエラーの即座失敗、リトライ不要エラーのリトライ | Warning |
| ログ不足 | エラーログにコンテキスト情報（何が・どこで・なぜ）がない | Suggestion |
| 正常異常混在 | エラーを戻り値で返すか例外で返すかが統一されていない | Warning |

### 5. パフォーマンス

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| N+1クエリ | ループ内のDB/API呼び出し | Critical |
| 不要な再計算 | キャッシュ可能な重い処理の繰り返し | Warning |
| メモリリーク | 解放されないリソース、肥大化するコレクション | Critical |
| 不要なコピー | 大きなオブジェクト/配列の不必要な深いコピー | Warning |
| 非効率なデータ構造 | 探索にリスト使用（O(n)）でマップ/セット（O(1)）が適切な場合 | Warning |

### 6. セキュリティ

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| SQLインジェクション | 文字列結合によるクエリ構築。パラメータ化クエリ必須 | Critical |
| コマンドインジェクション | ユーザー入力をシェルコマンドに展開 | Critical |
| XSS | ユーザー入力の未サニタイズ出力 | Critical |
| パストラバーサル | ユーザー入力由来のファイルパス未検証 | Critical |
| SSRF | ユーザー入力由来のURL未検証 | Critical |
| 認証認可欠落 | 未認証エンドポイント、権限チェック漏れ | Critical |
| 機密情報露出 | ログ/レスポンスへの秘密情報混入、ハードコードされた認証情報 | Critical |
| 入力バリデーション不足 | ホワイトリスト方式でないバリデーション、入力長上限なし | Warning |
| eval/動的コード実行 | `eval()`、信頼できないデータのデシリアライズ | Critical |
| CORS設定不備 | 必要以上に広いオリジン許可 | Warning |
| CSRFトークン欠如 | 状態変更リクエストにCSRF対策がない | Warning |
| 依存パッケージ脆弱性 | 既知脆弱性のあるパッケージの使用 | Warning |

### 7. テスト品質

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| テスト欠如 | 変更に対応するテストがない | Warning |
| アサーション不足 | `assert True` のみ、戻り値未検証 | Warning |
| エッジケース未カバー | 正常系のみ、異常系・境界値テストなし | Warning |
| AAA違反 | Arrange-Act-Assert のパターンに従っていない | Suggestion |
| テスト名不明瞭 | 何をテストしているか名前から読み取れない | Suggestion |
| モック過剰 | 実装詳細に密結合したモック。振る舞いではなく実装をテスト | Warning |
| テストの独立性欠如 | テスト間の依存・実行順依存・共有状態 | Warning |
| テストデータの不適切さ | マジックナンバー、意味不明なテストデータ | Suggestion |

### 8. 命名・可読性

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| 意図不明な命名 | 変数名/関数名から目的が読み取れない | Warning |
| 略語の乱用 | 検索不能な短縮名（`mgr`, `tmp`, `val` 等） | Suggestion |
| ブール値の命名 | `is_`, `has_`, `can_` プレフィックスの欠如 | Suggestion |
| 対概念の不一致 | open/close、start/stop 等の対が揃っていない | Suggestion |
| アーキテクチャ命名規則違反 | 該当ルールが存在する場合: `*Manager`, `*Provider`, `*Accessor` 規則に反する | Warning |
| 過度に長い関数 | 1関数が画面1枚を超える。分割の必要性 | Warning |
| ネスト過深 | if/for のネストが3段以上。早期リターンで平坦化すべき | Warning |

### 9. モダン性・イディオム

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| 非推奨API使用 | Deprecated な関数/メソッド/パッケージを使っていないか | Warning |
| 古いパターン | 言語の最新LTS版で推奨されるイディオムを使っているか | Warning |
| レガシー構文 | callback地獄→async/await、var→const/let 等の未移行 | Warning |
| 命令型ループ | map/filter/reduce 等の高階関数に置き換え可能な for/foreach | Suggestion |
| デッドコード | 未使用import、到達不能コード、コメントアウトされたコード放置 | Warning |

### 10. プロジェクト整合性

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| AGENTS.md規約違反 | プロジェクトのAGENTS.mdに記載された規約に反していないか | Critical |
| ルール違反 | `codex/rules/` に定義された制約に反していないか | Critical |
| 既存パターン無視 | プロジェクト内の既存コードと異なるスタイル/パターン | Warning |
| 一貫性の欠如 | 初見の開発者が「なぜここだけ違う？」と疑問に思う箇所 | Suggestion |

*Step 3 で展開したプロジェクト固有パターンをこのカテゴリに統合して検査する。*

### 11. 変更スコープ・互換性

| アンチパターン | 確認ポイント | 重要度 |
|----------------|-------------|--------|
| 破壊的変更 | 公開API/IFの署名変更、既存呼び出し元への影響 | Critical |
| 並行性・非同期 | async/awaitの誤用、race condition、デッドロック | Critical |
| 後方互換性未考慮 | 既存データ/設定との互換性が壊れていないか | Critical |
| スコープ逸脱 | 目的外の「ついでに」修正が混入していないか | Warning |

## 重要度基準

### Critical — マージ不可。必ず修正

本番障害・データ損失・脆弱性を引き起こす、または引き起こしうる問題。

| パターン | 例 |
|----------|----|
| セキュリティ脆弱性 | SQLインジェクション、XSS、コマンドインジェクション、eval() |
| データ破壊 | 不可逆なデータ変更、トランザクション不整合 |
| 未処理の致命的エラー | 本番でクラッシュする未捕捉例外 |
| 競合状態 | 共有リソースの非排他アクセスによるデータ破壊 |
| アーキテクチャ違反 | レイヤー依存方向逆転、横参照、段階飛ばし |
| 破壊的API変更 | 公開インターフェースの署名変更（既存呼び出し元が壊れる） |
| 規約違反 | AGENTS.md / `codex/rules/` の明示的禁止事項への抵触 |

### Warning — マージ前に対処推奨。3件以上で WARN 判定

バグの温床・保守性低下・技術的負債につながる問題。

| パターン | 例 |
|----------|----|
| 設計原則違反 | SRP違反、DRY違反（3箇所以上）、不要な複雑さ |
| エラーハンドリング不備 | エラー握り潰し、汎用キャッチ、リカバリ不適切 |
| パフォーマンス懸念 | 不要な再計算、非効率なデータ構造 |
| テスト不足 | 変更に対応するテスト欠如、モック過剰 |
| 命名・可読性 | 意図不明な命名、過度に長い関数、深いネスト |
| スコープ逸脱 | 目的外の「ついでに」修正 |
| 既存パターン不一致 | プロジェクト内の慣習と異なるスタイル |
| モダン性 | 非推奨API、レガシーパターン、デッドコード |

### Suggestion — 改善提案。対処は任意

より良いコードのための提案。対処しなくてもマージ判定に影響しない。

| パターン | 例 |
|----------|----|
| より良いアルゴリズム | 計算量の改善が可能だが現状でも許容範囲 |
| 命名の微改善 | 略語の展開、ブール変数のプレフィックス |
| テスト改善 | AAA準拠、テスト名改善、テストデータの意味明確化 |
| 一貫性の微調整 | 機能には影響しないスタイルの統一 |

**迷った場合は上位の重要度を適用する。**

## マージ判定

全チェック完了後、以下の基準で判定する。サマリーの先頭に表示すること。

| 判定 | 条件 | 意味 |
|------|------|------|
| **BLOCK** | Critical 1件以上 | マージ不可。Critical を全て解消するまでマージしてはならない |
| **WARN** | Critical 0件 かつ Warning 3件以上 | マージ前に対処推奨。Warning の大半を解消すべき |
| **PASS** | Critical 0件 かつ Warning 2件以下 | マージ可。残件は任意対応 |

---

## 自己検証プロトコル

指摘を出力する前に、以下を全て確認する:

1. **推測での指摘を含んでいないか** — 実コードで確認できない問題を指摘していないか
2. **修正案の構文は正しいか** — 提示するコードが構文エラーを含んでいないか
3. **既存テストへの影響を確認したか** — 修正案が既存テストを壊さないか
4. **存在しないAPIを使っていないか** — `hallucination-prevention` ルールのパターンを適用
5. **重要度が基準表に準拠しているか** — 重要度パターン基準表と照合し、恣意的な判定をしていないか
6. **アーキテクチャ違反を見逃していないか** — アーキテクチャ系ルールが存在する場合、import/依存グラフでルール違反を検査したか
7. **プロジェクト規約との整合性を確認したか** — AGENTS.md / `codex/rules/` の規約と変更内容を照合したか
8. **変更スコープが目的に対して過不足ないか** — 目的外の変更混入、または必要な変更の欠落がないか

## 出力形式

### 判定ヘッダー

```text
## 判定: [BLOCK|WARN|PASS]
```

### サマリー

| 重要度 | 件数 |
|--------|------|
| Critical | N件 |
| Warning | N件 |
| Suggestion | N件 |

### 各指摘

```text
### [重要度] カテゴリ名
N. ファイル:行 — 問題の要約
   （必要に応じて改行）
```

❌ **現状**:

```言語
// 問題のあるコード
```

✅ **修正案**:

```言語
// 修正後のコード
```

**理由**: 1文で問題と修正の根拠を説明。

## 禁止事項

| 禁止 | 理由 |
|------|------|
| 修正コードなしの指摘 | actionable でない |
| 「良い点」セクションの出力 | 問題発見に集中する |
