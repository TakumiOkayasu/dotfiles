# Error Recovery (障害復旧)

障害発生後の復旧・リカバリで壊れるケース。「壊れる瞬間」ではなく「壊れた後」に焦点。

## パターン一覧

### ER-01: ネットワーク断→再接続後の状態

- 攻撃: フォーム入力中にネットワークを切断 → 送信 → 再接続
- 検証: エラーが表示されるか。再接続後にリトライ可能か。入力内容が保持されるか
- 壊れ方: 無言で送信失敗、入力内容消失、二重送信
- 嫌度: ★★★★★

### ER-02: 部分保存からのリカバリ

- 攻撃: 親子テーブルへの保存中に親だけ成功・子が失敗した状態を作る
- 検証: 不整合状態の検出手段があるか。再実行で修復可能か
- 壊れ方: 孤児レコード、再保存時に主キー重複
- 嫌度: ★★★★★

### ER-03: バッチ中断→再実行の冪等性

- 攻撃: バッチ処理(集計、データ移行等)を途中で強制停止 → 再実行
- 検証: 処理済みデータが二重処理されないか。再開ポイントから継続できるか
- 壊れ方: 集計値が倍になる、重複レコード、中間テーブルのゴミ
- 嫌度: ★★★★★

### ER-04: DBコネクション枯渇後の復帰

- 攻撃: コネクションプール上限に達した状態で新規リクエスト → コネクション解放後
- 検証: 適切なエラーが返るか。解放後に正常復帰するか。コネクションリークがないか
- 壊れ方: 永続的に接続不可、タイムアウト後もプールが回復しない
- 嫌度: ★★★★★

### ER-05: ストレージ容量不足後の復帰

- 攻撃: ディスク容量不足でファイル保存・ログ書き込みが失敗 → 容量確保後
- 検証: エラーが検知されるか。中途半端なファイルが残らないか。復帰後に正常動作するか
- 壊れ方: 0byteファイル残存、ログ欠損で障害調査不能
- 嫌度: ★★★★☆

### ER-06: 外部API障害時のフォールバック

- 攻撃: 依存する外部API(認証、決済、メール送信等)がタイムアウト or 5xx
- 検証: タイムアウト設定が適切か。リトライ回数に上限があるか。フォールバックがあるか
- 壊れ方: 無限リトライでリソース消費、決済完了だがアプリ側エラー表示
- 嫌度: ★★★★★

### ER-07: キャッシュ破損後の整合性

- 攻撃: Redis/memcached等のキャッシュをフラッシュ or 一部キー消失
- 検証: キャッシュミス時にDBから正しく再取得するか。古いキャッシュが残らないか
- 壊れ方: 画面表示が古いまま、セッション情報消失でログアウト
- 嫌度: ★★★★☆

### ER-08: デプロイ中のリクエスト

- 攻撃: アプリケーションのローリングデプロイ中にリクエスト送信
- 検証: 旧バージョンと新バージョンでリクエストが混在しないか。マイグレーション中のDB操作
- 壊れ方: 新APIに旧フォーマットのリクエスト、マイグレーション中のカラム不在エラー
- 嫌度: ★★★★☆

### ER-09: ブラウザクラッシュ後の下書き復元

- 攻撃: 長文入力中にブラウザがクラッシュ → 再起動 → 同じ画面にアクセス
- 検証: 自動保存(ドラフト)機能があるか。localStorage/sessionStorageの復元
- 壊れ方: 30分の入力が全て消失
- 嫌度: ★★★★☆

### ER-10: ログ・監査証跡の欠損

- 攻撃: エラー発生時の操作ログ、障害復旧後の監査証跡を確認
- 検証: エラー前後の操作が追跡可能か。復旧操作自体がログに残るか
- 壊れ方: 「何が起きたか分からない」状態、コンプライアンス違反
- 嫌度: ★★★★★
