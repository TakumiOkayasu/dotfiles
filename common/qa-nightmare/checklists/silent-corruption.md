# Silent Corruption (サイレントデータ破損)

UIは正常に見えるが、DBが壊れているケース。最も発見が遅れ、被害が大きい。

## パターン一覧

### SC-01: ロールバック漏れ

- 攻撃: トランザクション内の2テーブル更新で、2つ目を意図的に失敗させる(FK違反等)
- 検証: 1つ目のテーブルもロールバックされているか
- 壊れ方: 親レコードだけ残り子レコードがない孤児データ
- 嫌度: ★★★★★

### SC-02: 小数点丸め累積

- 攻撃: 単価 × 数量の計算を100回繰り返す(0.1 × 3 = 0.30000000000000004 問題)
- 検証: 集計値がDBの値と画面表示で一致するか
- 壊れ方: 月末集計で1円〜数百円のズレ
- 嫌度: ★★★★☆

### SC-03: 文字コード化け保存

- 攻撃: UTF-8の4バイト文字(𠮷、🍣)、サロゲートペア、ゼロ幅スペースを入力
- 検証: DB保存後に再取得して入力値と一致するか
- 壊れ方: 保存は成功するが再表示で文字化け or 検索不一致
- 嫌度: ★★★★☆

### SC-04: NULLと空文字の混同

- 攻撃: 任意入力フィールドを空欄のまま保存
- 検証: DBに NULL が入るか空文字 '' が入るか。検索・フィルタで両方ヒットするか
- 壊れ方: WHERE column IS NULL で空文字レコードが漏れる
- 嫌度: ★★★★☆

### SC-05: 自動採番のギャップ

- 攻撃: レコード作成 → 即削除 → 再作成を10回繰り返す
- 検証: 採番が連番であることを前提としたロジック(「前回+1」等)が壊れないか
- 壊れ方: 欠番を許容しないビジネスロジックが破綻
- 嫌度: ★★★☆☆

### SC-06: タイムスタンプの上書き

- 攻撃: レコードAを更新 → 別ユーザーがレコードAを参照 → 最初のユーザーが再更新
- 検証: updated_at が正しいか。楽観ロック用のバージョンカラムが機能するか
- 壊れ方: 更新履歴が実態と一致しない
- 嫌度: ★★★★☆

### SC-07: カスケード削除の漏れ

- 攻撃: 親レコードを削除
- 検証: 関連する子・孫レコードが全て削除(or 論理削除)されているか
- 壊れ方: 孤児レコードが残り集計に悪影響
- 嫌度: ★★★★★

### SC-08: デフォルト値の不整合

- 攻撃: 必須でないカラムを一切指定せずにINSERT
- 検証: DBのDEFAULT値とアプリの想定デフォルトが一致するか
- 壊れ方: アプリは0のつもりがDBにNULLが入り、計算でNaN
- 嫌度: ★★★★☆

### SC-09: 論理削除レコードの再表示

- 攻撃: 論理削除済みレコードを含むテーブルで一覧検索
- 検証: 削除済みが表示されないか。集計に含まれないか
- 壊れ方: 削除したはずのデータが売上集計に含まれる
- 嫌度: ★★★★★

### SC-10: 外部キー参照先の論理削除

- 攻撃: 受注の顧客マスタを論理削除
- 検証: 既存の受注画面で顧客名が表示されるか。新規受注で選択不可になるか
- 壊れ方: 顧客名が空欄 or エラー
- 嫌度: ★★★★☆
