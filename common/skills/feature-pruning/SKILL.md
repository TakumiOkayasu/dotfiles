# Feature Pruning (機能粒度の棚卸し - 戦術レベル)

設計が固まり、実装する機能リストが揃った段階で、**個別機能の 1 つ 1 つを名指しで「これ本当に要る?」と問い直す**のが本 skill の核。「ページネーション (件数 30 件で 1 ページに収まる)」「確認ダイアログ (取り消し可能操作で警告不要)」「印刷ボタン (ブラウザ標準で代替可能)」レベルの具体指摘を、バイアスを排した実行者から取り出す。最低 3 ラウンド、機能名で語ることを強制する。

**本 skill の責務範囲は「個別機能の要否」まで**。「方針自体が筋が良いか」は別 skill (`premise-questioning`) で扱う。順序は **premise-questioning (戦略) → feature-pruning (戦術)**。方針自体が間違っていたら、機能を削っても無意味。

## トリガー条件

- UI 設計レビュー (画面 / コンポーネントの要素確定直前)
- API 設計レビュー (エンドポイント / クエリパラメータ確定直前)
- データモデル設計レビュー (テーブル / カラム確定直前)
- 実装着手直前の機能棚卸し (premise-questioning で方針が ✅ になった後)
- 既存画面 / API の機能削減レビュー (使われていない機能の炙り出し)
- 「機能てんこ盛り」傾向のある設計の見直し: ページネーション・検索・フィルタ・ソート・確認ダイアログ・保存ボタン・通知バッジ等が「とりあえず付いている」設計

使わない場面:

- 方針自体が固まっていない段階 → `premise-questioning` を先に
- 機能リストが箇条書きで列挙されていない段階 (入力が成立しない)
- typo 修正 / コメント修正 / dependency bump など軽微な変更
- 締切が迫って意思決定の余裕がないとき

## ワークフロー

1. **対象機能リストのパッケージ化**

- **機能 / UI 要素 / API エンドポイント / データ列を箇条書きで全列挙する** (これを欠かすと skill が成立しない)
  - 必須情報:
  - 機能リスト (例: 「画面 A: ヘッダー / 検索ボックス / フィルタ / リスト本体 / ページネーション / 確認ダイアログ / 保存ボタン / フッター」)
  - 想定データ量 (件数 / レコード数 / 同時利用ユーザー数)
  - 想定ユーザー行動 (主要動線、推定使用頻度)
  - 環境前提 (Web / iOS / Android / デスクトップアプリ等。標準機能の利用可否に効く)
- 任意情報:
  - 既存代替手段の候補 (ブラウザ機能 / OS 機能 / 既存ツール等で思い当たるもの)

1. **手法ローテートで 3 ラウンド dispatch**

- Round 1: **YAGNI Probe** (機能要否プローブ) - 各機能の使用確率を時系列で見積もり、低確率機能を炙り出す
- Round 2: **Convention Audit** (慣習監査) - 慣習で入れているだけの機能を炙り出す
- Round 3: **Existing Substitute** (既存代替検証) - 標準機能 / 既存ツールで代替可能な機能を炙り出す
- **毎回新規 subagent を Task tool で dispatch** する (前回の出力を学習させない)。並列実行して構わない
  - dispatch 不能環境の扱いは「環境制約」節

1. **機能ごとの 3 軸スコアリング** (各軸 0-5、判定文言は「スコア軸」節で一元定義)

   - subagent が **機能リストの全項目について** 3 軸を採点する (機能数 × 3 軸のマトリクス)

- 3 リスト必須出力: 過剰機能リスト / 不足機能リスト / 代替可能機能リスト

1. **ラウンド間統合**

- 3 ラウンド × 機能数 × 3 軸 = N セルを統合
- **3 リストの和集合** を取る (Round 1 で出た過剰機能 ∪ Round 2 で出た過剰機能 ∪ Round 3 で出た過剰機能)
- 機能ごとの **削減判定**: ✅ 維持 / 🟡 縮小 / 🔴 削除 / 🔁 標準機能で代替

1. **収束判定** (詳細は「反復の打ち切り基準」節)

- 3 ラウンドで同じ機能が 2 回以上「過剰 / 代替可能」判定 → 削除候補確定
- 1 ラウンドだけの指摘 → Round 4 で再検証 (制約除去 or 競合手法の追加投入)

1. **結論アウトプット**

- 維持機能リスト / 縮小機能リスト / 削除推奨リスト / 標準機能代替リスト
- 削減後の最終機能セット (Before / After 対比)
- 削減によるリスク (もし削ったら困るシナリオ)

## 3 つの手法 (Core 3、ラウンドごとにローテート)

### Round 1: YAGNI Probe (機能要否プローブ)

問い: 「機能リストを 1 つずつ取り上げ、それぞれについて『今リリース時に使われる確率』『6 ヶ月後に使われる確率』『1 年後に使われる確率』を 0-100% で見積もれ。今リリース時の使用確率が 50% 未満の機能を全て名指しで列挙せよ。さらに使用確率の根拠 (想定データ量 / ユーザー行動 / 推定頻度) を添えよ」

検出しやすい問題:

- データ量に対して過剰な機能 (件数 30 件でページネーション、件数 5 件でソート機能等)
- 使用頻度の低い機能 (印刷 / エクスポート / 詳細フィルタ等で実使用率 5% 未満)
- 「将来使うかも」で入れた機能 (実際には 6 ヶ月経っても使われない)

弱点: 使用確率の見積もり精度依存。データ量 / ユーザー行動の前提が薄いと精度が落ちる

### Round 2: Convention Audit (慣習監査)

問い: 「現状の機能リストに含まれる機能 / UI 要素のうち『業界 / フレームワーク / 過去プロジェクトの慣習で入れているだけで、本案件の固有要件としては必要性を説明できない』ものを名指しで全列挙せよ。各項目に『慣習由来の度合い』を 0-5 で採点せよ。さらに、慣習由来の機能が無いと困る具体シナリオを示せるか検証せよ (示せないなら不要)」

検出しやすい問題:

- 「とりあえず付ける」UI 要素 (パンくずリスト / footer / ヘルプアイコン / 設定ボタン等)
- 「他の管理画面でもあるから付ける」系 (検索ボックス / ソート / フィルタ / ページネーション)
- 装飾的な機能 (通知バッジ / アニメーション / ローディング演出等で UX への寄与不明なもの)

弱点: 「慣習の中に意味があるもの」を一律で疑うと過剰削減に倒れる。「困るシナリオを示せるか」で歯止めをかける

### Round 3: Existing Substitute (既存代替検証)

問い: 「現状の機能リストに含まれる機能のうち、ブラウザ標準機能 / OS 標準機能 / 既存ツール / SaaS / フレームワーク標準コンポーネントで代替可能なものを名指しで全列挙せよ。各項目に『代替可能性』を 0-5 で採点し、代替手段名を具体的に書け」

検出しやすい問題:

- 自前検索ボックス → ブラウザ Cmd+F で代替
- 自前戻るボタン → ブラウザ戻るで代替
- 自前印刷機能 → ブラウザ標準印刷で代替
- 自前 CSV エクスポート → 表のコピペで代替 (件数少ない場合)
- 自前ファイルアップローダ → input[type=file] そのまま
- 自前日付ピッカー → input[type=date] そのまま
- 自前トースト通知 → ネイティブ通知 API
- 自前モーダル → dialog 要素

弱点: 環境制約 (古いブラウザ対応 / アクセシビリティ要件) を見落とすことがある。「環境前提」を入力に必ず含める

### 拡張モード (Round 4 以降で発動)

3 ラウンドで結論が割れたとき、または 1 ラウンドだけの指摘で確信が持てないとき:

- **制約除去** - 「予算 / 工数 / 既存資産 / 互換性の制約を全部外したら、この機能は要るか」
- **競合手法再投入** - YAGNI Probe / Convention Audit / Existing Substitute から、初回と異なる切り口で再 dispatch (例: 初回は使用確率ベース、2 回目はデータ量ベース)

## 採点根拠の引用形式

各機能・各軸の採点根拠は **(a) 必須 / (b) 併記推奨** の 2 行で書く (判定の追跡可能性のため):

- (a) 判定文言引用 **(必須)**: 下記「スコア軸」節の該当点の文言を逐語引用する (例: 「F-Nec=1: 想定使用頻度 5% 未満 / データ量に対して過剰」)
- (b) 数値根拠 **(具体数値が出せる場合は必須)**: 想定件数 / 使用率 / 推定頻度 等の具体値で示す (例: 「F-Cnv=4: 業界慣習由来 80%、本案件固有要件で説明できるのは『XX』機能のみ」)

(b) を「具体数値が出せない」と省略する場合、採点が判定文言からの推測に留まっている可能性が高く、**再 dispatch 案件**。抽象表現 (「便利そう」「使いそう」「慣習だから」) は NG。subagent レポートで全機能・全 3 軸の採点根拠がこの形式で書かれていない場合は再 dispatch する。

## スコア軸 (機能ごと、判定文言の一元定義)

「軸名から推測した採点は判定文言に届かない」(empirical の教訓)。各点の判定基準を文言レベルで固定する。

### F-Necessity (機能必要性) — 低スコアほど削減候補

- 5: その機能なしには主要動線が成立しない (代替なし、頻繁に使われる)
- 4: 主要動線で必要だが、削っても代替手段で 1 段階多いクリックで到達可能
- 3: あった方が UX が良いが、なくても主要動線は回る
- 2: 一部のユーザーシナリオで便利だが、削っても大半のユーザーは困らない
- 1: 想定使用頻度 5% 未満 / データ量に対して過剰
- 0: 想定使用頻度ほぼゼロ / 機能の必要性を説明する具体シナリオが示せない

### F-Convention (慣習由来度) — 高スコアほど削減候補

- 5: 慣習由来 100%、本案件の固有要件で必要性を説明できない
- 4: 慣習由来が大きく、本案件固有要件で部分的にしか説明できない
- 3: 慣習が大きいが、一部の本案件固有の要件もある
- 2: 慣習要素はあるが、本案件固有の要件由来が主
- 1: 本案件固有の要件が主、慣習は補助的
- 0: 完全に本案件固有の要件由来、慣習要素ゼロ

### F-Substitutable (代替可能性) — 高スコアほど自前実装不要

- 5: ブラウザ標準機能 / OS 標準機能で完全代替可能、自前実装不要
- 4: 既存社内ツール / 画面外サービス (社内 wiki / IDP / BI 等) で代替可能 (画面から機能を移動)
- 3: 既存ライブラリ / フレームワーク標準コンポーネントで代替可能
- 2: 部分代替可能、固有 UX 要件の半分以上は自前実装が必要
- 1: 部分代替可能だが、固有 UX 要件の一部は自前実装必要
- 0: 完全に自前実装が必要 (代替手段なし)

### 削減判定ルール (優先順位明示)

機能ごとの 3 軸スコアから判定する。複数の判定条件が同時に成立する場合は **上から順に優先**:

- **🔴 削除推奨** (最優先): F-Nec ≤ 1 (使われない) または F-Cnv ≥ 4 かつ F-Nec ≤ 2 (慣習由来かつ低必要性)
- **🔁 標準機能で代替** (次点): F-Sub ≥ 4 (代替可能性が高い) かつ F-Nec ≥ 2 → 自前実装をやめて標準機能 / 画面外サービスに置換
- **🟡 縮小**: F-Nec = 2-3 かつ他軸でも要検討 (機能を残すが規模を縮小)
- **✅ 維持**: F-Nec ≥ 4 かつ F-Cnv ≤ 2 かつ F-Sub ≤ 2 (本案件固有で必要、自前実装が妥当)

**判定の使い分け**:

- 🔴 削除と 🔁 代替の境界は **F-Nec の値** で決まる (≤ 1 → 🔴 / ≥ 2 → 🔁)。F-Sub ≥ 4 でも F-Nec ≤ 1 なら 🔴 削除を優先する (使われない機能は代替先に移しても無駄)
- 画面外代替 (社内 wiki / IDP / BI 等) の場合は F-Sub = 4 として採点し、F-Nec ≥ 2 なら 🔁、F-Nec ≤ 1 なら 🔴。代替先は「代替可能機能リスト」で必ず明示する

**ライブラリ採用前提時の 🔴 / 🔁 境界** (F-Sub=3 の特例):

- 同等機能を提供するライブラリ (テーブルライブラリ / フォームライブラリ / 認証ライブラリ等) の採用が前提条件として確定 / 強く推奨されている場合、F-Sub=3 (既存ライブラリで代替可能) でも **🔁 を優先**する (付随で得られる機能を再実装しない)
- ライブラリ未採用 / 採用判断未確定の場合は、F-Nec ≤ 1 → 🔴 ルールを通常通り適用する (使用率低い機能を自作する工数 > 自作回避メリット)
- 判定例:
  - ソート (F-Nec=1, F-Cnv=4, F-Sub=3) で TanStack Table 採用前提 → **🔁 (ライブラリ付随取得)**
  - ソート (F-Nec=1, F-Cnv=4, F-Sub=3) で表を自作する場合 → **🔴 削除** (使用率 3% に対して自作工数の方が大きい)
- 入力側でライブラリ採用前提の有無を明示する (前提不明時は subagent が「ライブラリ未採用」とみなして採点)

**ばらつきとの競合解決**:

- 「マトリクス集約ルール」(提示フォーマット節) のラウンド間ばらつき ±2 以上 → 判定保留+追加ラウンド発動と、本節の優先順位 (🔴 削除推奨 / 🔁 代替) で結論が確定する条件が同時に成立した場合は **本節の優先順位を優先** = 判定保留せず確定
- 具体例: F-Cnv が R1=2 / R2=4 / R3=4 (ばらつき 2) でも、F-Nec ≤ 1 が 3R 安定なら 🔴 削除推奨を確定 (追加ラウンド不要)
- 理由: 保留して追加ラウンドを回しても結論が変わらない場合、ラウンド追加はリソースの無駄。ばらつき判定保留が意味を持つのは「ばらつき軸が判定の決め手になっている」ケースのみ

## 環境制約

新規 subagent を dispatch できない環境では本 skill は **適用しない**。

- 代替案 1: 親セッションのユーザーに別 Claude Code セッションでの確認を依頼
- 代替案 2: スキップを明示報告 (「feature-pruning skipped: dispatch unavailable」)
- **NG**: 自分で 3 手法を順に当てて自己評価する (バイアス排除の構造が崩れる)

**簡易モード**: 機能数が少ない (5 個未満) / 重要度が低いとき、**1 ラウンド (YAGNI Probe のみ) + 自己採点** に縮退。ただし「3 ラウンドで採点した」とは言わない (混同回避)。

## 反復の打ち切り基準

- **収束 (削減判定確定)**:
  - 3 ラウンド全てで「過剰機能リスト / 代替可能機能リスト」の和集合が同じ機能を 2 回以上含む → その機能の削減 / 代替判定を確定
  - 全機能の削減判定が ✅ / 🟡 / 🔴 / 🔁 のいずれかに確定
- **追加ラウンド発動**:
  - 1 ラウンドだけで指摘された機能が複数あり、確信が持てない
  - 結論ラベル (機能リスト全体) がラウンド間で割れる
  - → 拡張モード (制約除去 / 競合手法再投入) を Round 4-5 として追加投入
- **発散 (設計を疑う)**:
  - 5 ラウンド回しても削減判定が割れ続ける機能がある → そもそも機能の必要性が前提から不明確。premise-questioning に戻り、方針レベルで再検証する
- **過適合チェック**:
  - 削減判定が出た直後、**hold-out として削減後の機能セットを 1 ラウンド回し、「不足機能はないか」を改めて検証**。新たな不足が出れば削減判定を疑う

## Red flags (合理化に注意)

| 出てくる合理化 | 実態 |
| --- | --- |
| 「自分で 3 つの視点を順に考えれば dispatch 不要」 | 直前に書いた機能リストを客観視はできない。dispatch 必須 |
| 「機能数多いから抜粋で採点しよう」 | 抜粋すると見落とす。全項目スコアマトリクス必須 |
| 「『過剰機能なし』で済ませたい」 | 機能リスト全項目の検討根拠を示せていなければ採点不能。サボらせない |
| 「抽象的に『機能多い』と言うだけで具体機能名は出さない」 | 具体性ゲート違反、再 dispatch 案件 |
| 「2 ラウンドで結論一致したから 3 ラウンド目省略」 | 3 つの手法は別の盲点を持つ。省略すると Existing Substitute 系の指摘が漏れる |
| 「過剰機能リスト 1 機能だけだから無視しよう」 | 1 機能でも実装コストは積み上がる。判定リストには載せる |
| 「削除推奨を全部即実行したい」 | hold-out チェック (削減後セットで不足検証) を経てから実行 |
| 「方針自体に疑問が出た」 | 本 skill の責務外。premise-questioning に戻る |

## よくある失敗

- **機能リストのパッケージが薄すぎる**: 「画面 A を作る」では subagent が機能粒度に降りられない。「画面 A: ヘッダー / 検索ボックス / フィルタ / リスト本体 / ページネーション / フッター」のレベルで列挙する
- **データ量を書かない**: 「ページネーション要らない (件数 30 件で 1 ページに収まる)」級の指摘は想定件数なしには出せない
- **環境前提を書かない**: Web / iOS / Android / デスクトップで標準機能の利用可否が変わる。Existing Substitute の精度に直結
- **3 軸スコアマトリクスを「全項目埋める」を強制しない**: 抜粋採点になり、見落とした機能が削除候補から漏れる
- **過剰機能と不足機能の片方だけ見る**: 削減ばかりで不足を見ないと「削った後に必須機能が足りない」事態に。3 リスト揃えて見る
- **削減判定を即適用**: hold-out チェック (削減後セットで不足検証) を必ず挟む。削減後に「あれ、これ要るやつだった」を防ぐ
- **方針レベルの疑問を本 skill に持ち込む**: 「そもそもこの画面要る?」は premise-questioning の領域。混ぜない
