# Implementation Policy

現在の要件を満たす最小の技術構成を選ぶ. 技術選定・ライブラリ利用・データアクセスの共通指針であり, project の契約・運用要件・言語の規約を優先する.

## 基本

- 標準ライブラリ / 既存依存 / 採用済みフレームワークで要件を満たせるか先に確認する. 新しい依存は total complexity を下げるか reliability を高める場合に選ぶ
- 自前実装を選ぶ場合は, 既存手段との cost・contract の違いを説明する. 権限・秘密・本番変更等の承認が必要な境界は project の gate に従う
- 汎用ユーティリティ (配列・オブジェクト操作, 日時, UUID, 乱数, エンコード, 正規表現) は再発明しない
- 計算量は実際の入力規模・上限・性能予算から選ぶ. bounded input の適正な処理を計算量の分類だけで棄却しない. 外部入力には必要な上限を設け, CPU・メモリの過大消費を計測や boundary test で確認する

## 依存管理

- 新規ライブラリ追加前に、既存依存で代替できないか確認する
- 利用実績, maintenance・security 状況, project の license 条件との適合, 運用 cost を確認する. 最終 commit の新しさや license 名だけで採否を決めない
- lockfile は必ずコミットする。`latest` / ワイルドカード指定はしない
- 依存の追加・更新時に脆弱性スキャン (npm audit, pip-audit 等) を実行する

## 領域ごとの選択と守る境界

| 領域 | 方針 |
| --- | --- |
| DB アクセス | 既存の data access contract を維持する. ORM / query builder / parameterized SQL は既存依存・必要な query・運用要件から選ぶ. ORM の追加を一律に要求しない |
| スキーマ変更 | マイグレーションツール経由。本番 DDL の直接実行をしない |
| ロギング | 運用ログは標準または既存の logging 機能で level・文脈を扱い, 機密情報を出さない. CLI の標準出力など出力契約を持つデータと運用ログを区別する |
| バリデーション | システム境界で必要な contract を検証する. 単純な型・範囲検証は標準機能でよく, 複雑な schema は既存または定評 library を必要に応じて使う |
| 暗号・ハッシュ | 自前実装をしない。言語標準または定評ライブラリのみ。アルゴリズムは公式推奨に従う |
| HTTP クライアント | 同じ通信責務で既存の client を再利用する. runtime・protocol・認証境界が異なる場合は必要な client を選び, 数を揃えるための wrapper を追加しない |
| 設定値 | 秘密・環境ごとの差・運用で変える値は環境変数や設定ファイルで扱う. 不変の domain / protocol 定数を機械的に外部化しない |

## SQL の判断と安全性

SQL を使う場合は, 外部入力の値を文字列連結せず prepared statement / parameter binding を使う. DB contract や運用方式の変更は理由を PR に記載し, project の review・migration・本番承認 gate を維持する. 次は選択を検討する例であり, 許可対象の網羅表ではない.

- バルク処理: パフォーマンス計測結果を根拠に示す
- 複雑な集計 (CTE / window 関数): ORM で表現困難なことを示す
- DB 固有機能: 移植性を捨てる判断を明示する
- 読み取り専用レポート: ビュー定義または生 SQL、レビュー必須
