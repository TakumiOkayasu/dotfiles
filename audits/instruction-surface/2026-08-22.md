## Executive summary

### Scope

Canonical or behavior-owning assets reviewed:

- 18 shared skills under `common/skills/`
- 4 shared commands under `common/commands/`
- 8 shared rules under `common/rules/`
- 6 Claude custom-agent definitions and their Codex counterparts

- global surfaces: `AGENTS.md`, `CLAUDE.md`, `claude/settings.json`, `claude/SUBAGENTS.md`, `codex/SUBAGENTS.md`
- generated workflow definitions in `scripts/generate-standard-workflow-skills.py`
- generated Codex views for drift and activation differences

### User-reported symptoms

The user reported behavior corresponding to:

- reasoning that appears less capable than the underlying model
- excessive explanation and ceremony around straightforward work
- repeated verification and self-review
- unnecessary subagent delegation
- increased latency and tool use
- older instructions constraining newer models

These are observed symptoms, not proven causes.

- `KEEP`: 7

### Main findings

1. **Mandatory reasoning and delegation chains have a `STRONG` relationship to latency, token use, and ceremonial output.**  
   `feat`, `premise-questioning`, `feature-pruning`, `design-team`, `orchestrate`, and `deep-review` prescribe fixed rounds, fixed agent counts, minimum alternatives, or mandatory review stages even when a strong parent model could resolve the task directly.

2. **The hook surface has a `STRONG` relationship to automatic overhead and a `POSSIBLE` relationship to perceived model quality.**  
   `UserPromptSubmit`, `Stop`, `PostToolUse`, and `SessionStart` collectively invoke broad reminders, completion checks, failure logging, primary-source checks, notes handling, and vendor updates.

3. **Several assets encode model- or harness-specific assumptions.**  
   Examples include `opus-47-policy`, fixed `sonnet` reviewer selection, Haiku/Sonnet/Opus escalation language, and workflows that fail when subagents are unavailable rather than allowing the parent model to continue.

4. **Durable project knowledge remains valuable.**  
   Canonical-source rules, generation procedures, destructive-operation restrictions, interface-first small development, empirical measurement, systematic debugging, and reproducible verification should remain.

5. **Code review lacked an explicit human approval gate for prohibited or irreversible operations.**  
   This PR adds that gate separately from the read-only audit. Passing tests or static analysis does not waive the requirement.

### Non-instruction factors

The following may also contribute and are not proven causes:

- globally high effort settings
- 1M-context model configuration
- tool startup and remote-control behavior
- plugin loading and marketplace configuration
- context compaction and memory behavior
- runtime-level routing and model selection

### Incomplete scopes

- Managed/enterprise instructions outside the repository were not available.
- Installed third-party plugin skills were not exhaustively read.
- Runtime benchmarks were not executed.
- Static analysis cannot establish that a specific asset caused a symptom.

The audit itself made no changes to reviewed assets or settings.

## Findings requiring action

### 1. Mandatory reasoning and delegation chain

**Outcome**

Prevent poorly considered features and catch mistakes before implementation.

**Evidence**

- `common/commands/feat.md`: loads multiple methodology skills before work, conditionally requires complete `premise-questioning` and `feature-pruning` workflows, mandates `qa-nightmare`, and waits for explicit test-design approval.
- `common/skills/premise-questioning/SKILL.md`: minimum three independent subagent rounds and additional rounds when results differ.
- `common/skills/feature-pruning/SKILL.md`: minimum three independent rounds, per-feature scoring, and convergence rounds.
- `common/skills/design-team/SKILL.md`: two independent agents, at least five alternatives, synthesis, and a second adversarial review.
- `common/skills/orchestrate/SKILL.md`: one fresh subagent per task, fixed micro-step planning, specification review, then deep review.
- `common/commands/deep-review.md`: exactly three subagents and BLOCK when dispatch is unavailable.

**Symptom relationship**

`STRONG` for latency, subagent count, token use, long output, and repeated verification.  
`POSSIBLE` for lower answer quality because the model is constrained to follow mechanisms instead of selecting the minimum sufficient reasoning path.

**Preserve**

- explicit high-risk escalation
- independent review when the cost of a blind spot is high
- YAGNI and premise challenge as optional lenses
- reproducible review output for real release gates

**Remove or reconsider**

- fixed round counts
- fixed agent counts
- minimum alternative counts
- mandatory score matrices
- automatic use on ordinary changes
- blocking when the parent can safely continue without subagents

**Recommendation**

Rebuild the heavy workflows around risk-based optional lenses. Confidence: `HIGH`.

**Next validation**

Run the same small feature, medium feature, and high-risk design in fresh sessions with the current chain enabled and with a risk-routed minimal chain. Compare constraint compliance, defects found, elapsed time, tokens, subagent calls, tool calls, and user edits.

### 2. Automatic hook amplification

**Outcome**

Enforce safety, honest completion claims, primary-source use, session continuity, and environment readiness.

**Evidence**

`claude/settings.json` registers 21 unique hook scripts across PreToolUse, PostToolUse, UserPromptSubmit, Stop, PreCompact, and SessionStart. Automatic methodology and primary-source prompts run before or at every user interaction; three checks run at Stop; session startup includes reminders, resume, environment checks, vendor updates, primary-source reminders, and notes loading.

**Symptom relationship**

`STRONG` for automatic hook count and potential latency.  
`POSSIBLE` for verbosity, repeated warnings, and perceived over-cautious behavior.

**Preserve**

- deterministic destructive-command, privilege, secret, and sensitive-file blockers
- lifecycle-specific backups
- narrowly scoped environment checks

**Remove or reconsider**

- methodology reminder on every prompt
- duplicated primary-source reminder/check
- multiple overlapping Stop checks
- network updates during interactive startup
- PostToolUse work after every Bash command

**Recommendation**

Consolidate hooks by concern and narrow triggers before removing safety controls. Confidence: `HIGH`.

**Next validation**

Record hook execution count and wall time for a representative session. Disable one duplicate group at a time in fresh sessions and compare safety regressions, latency, injected text, and user-visible interruptions.

### 3. Model- and harness-specific policy

**Outcome**

Select suitable model effort and delegation behavior.

**Evidence**

- `common/rules/opus-47-policy.md` is named for a specific model generation.
- `claude/agents/code-reviewer.md` pins `model: sonnet`.
- several workflows refer to Haiku/Sonnet/Opus escalation.
- multiple skills treat subagent availability as a hard requirement rather than one implementation option.

**Symptom relationship**

`POSSIBLE`: stale routing can underuse the current parent model or fail in a different harness.

**Preserve**

- explicit cost/risk routing
- known tool capability constraints
- reproducibility when a model pin is empirically required

**Remove or reconsider**

- model-version names as policy owners
- unconditional fixed model tiers
- blocking solely because a historical delegation mechanism is unavailable

**Recommendation**

Rebuild as capability-, cost-, and risk-based runtime policy. Confidence: `HIGH`.

**Next validation**

Benchmark the same tasks with current routing and capability-based routing while holding the actual model constant.

### 4. Overlapping strategy and design assets

**Outcome**

Question the problem, prune unnecessary scope, compare designs, and place responsibilities.

**Evidence**

`consult`, `premise-questioning`, `feature-pruning`, `design-team`, `arch`, and `interface-first-design` all participate before implementation and have partially overlapping trigger language.

**Symptom relationship**

`POSSIBLE` for unintended activation, duplicate analysis, and user confusion over which workflow owns the decision.

**Preserve**

- `interface-first-design`: current-use-case contract design
- `arch`: responsibility placement after contracts
- one explicit high-risk challenge workflow
- one concise user-facing consultation format

**Remove or reconsider**

- separate mandatory workflows for every reasoning lens
- overlapping natural-language triggers
- workflow chaining encoded in multiple locations

**Recommendation**

Keep `interface-first-design` and `arch` as canonical design owners; rebuild or merge the challenge/consultation assets around explicit risk boundaries. Confidence: `HIGH`.

**Next validation**

Use historical design requests and measure activation precision, duplicated output, and whether one asset can produce the required decision without invoking another.

### 5. Semantic-writing overlap

**Outcome**

Produce natural Japanese with clear referents and avoid vague labels.

**Evidence**

`semantic-generation`, `referent-before-label`, and `natural-japanese` all own parts of referent selection, naming, and writing clarity.

**Symptom relationship**

`POSSIBLE` for verbose setup and duplicated guidance.

**Preserve**

One concise rule with project-specific writing constraints and one optional workflow for difficult naming/drafting tasks.

**Remove or reconsider**

Repeated examples and multiple canonical owners.

**Recommendation**

Merge ownership and validate whether the optional skill still improves real drafts. Confidence: `MEDIUM`.

**Next validation**

Compare real technical explanations with only the canonical rule versus rule plus skill. Evaluate clarity, verbosity, correction count, and user preference.

### 6. Human review gate for prohibited operations

**Outcome**

Ensure a person reviews changes that introduce operations the project declares forbidden, approval-gated, destructive, irreversible, privileged, secret-sensitive, production-affecting, or externally mutating.

**Evidence**

Safety rules and global policy restrict such operations, but the existing code-reviewer outputs only Critical/Warning/Suggestion and can otherwise report a normal pass when tests succeed.

**Symptom relationship**

`NONE FOUND` for the reported "less capable" symptom. This is a separate governance requirement explicitly requested by the user.

**Preserve**

AI evidence gathering, technical findings, and test evaluation.

**Add**

- mandatory `HUMAN_REVIEW_REQUIRED` marker
- evidence of the operation and its reachability
- intent, trigger, blast radius, rollback, safeguards, alternatives, and approval record
- no AI-only PASS or merge recommendation until a person records approval

**Recommendation**

Add the gate to global review policy and both Claude/Codex reviewer agents. Confidence: `HIGH`.

**Next validation**

Review a fixture diff that adds a forbidden destructive command and confirm every review entrypoint reports the human gate even when tests pass.
