# Systematic Debugging

## トリガー条件

- バグ・テスト失敗に遭遇したとき
- エラーメッセージが出たとき
- 期待と実際の動作が異なるとき

**入力**: バグの症状・エラーメッセージ・失敗しているテスト  
**出力**: 根本原因の特定 + TDDによる修正

---

## 鉄則

**推測での修正禁止。根本原因を特定してから修正。**

---

## 4フェーズ (スキップ禁止)

### Phase 1: 再現

100%再現可能にする。再現できなければ修正提案禁止。

```
- [ ] 症状を正確に記録
- [ ] 最小再現ケースを作成
- [ ] 環境情報を収集 (OS・バージョン・依存ライブラリ)
- [ ] 再現手順を文書化
```

**完了条件**: 同じ手順で毎回同じエラーが出ること

### Phase 2: 境界トレース

どの層で問題が発生しているか特定。

```
- [ ] フロントエンド / バックエンド / DB / 外部サービス
- [ ] どの時点でデータが壊れるか?
- [ ] 正常なケースと異常なケースの差分は何か?
```

**完了条件**: 問題が発生しているレイヤーと箇所を1つに絞り込めること

### Phase 3: 根本原因特定

「なぜ?」を繰り返す。

```
症状 → なぜ? → なぜ? → なぜ? → 根本原因
```

**完了条件**: 「〇〇が原因で〇〇が起きている」と1文で説明できること

### Phase 4: TDDで修正

1. バグを再現するテストを書く (RED)
2. 最小限の修正 (GREEN)
3. リグレッションがないことを確認

**完了条件**: 追加したテストがパスし、既存テストが全てパスすること

---

## 使用例

```
ユーザー: "pytest tests/test_api.py::test_login が失敗しています"

→ Phase 1: エラーメッセージ全文を取得・最小再現コードを特定
→ Phase 2: API層 / 認証層 / DB層のどこで失敗しているか絞り込み
→ Phase 3: なぜ認証が失敗するか → トークン期限切れ → なぜ? → 時刻比較がUTCとローカル混在
→ Phase 4: 時刻比較のテスト追加(RED) → UTC統一修正(GREEN) → 全テスト確認
```

---

## 失敗パターン

**3回以上の修正失敗 → アーキテクチャを疑う。ユーザーと相談。**

---

## デバッグ記録テンプレート

```
## バグ: [一行サマリ]
### 再現手順: 1. ... 2. ...
### 環境: OS / バージョン
### エラーメッセージ: (原文)
### 試したこと: [内容] → [結果]
### 根本原因:
### 修正方針:
```

---

## 禁止事項

- 推測だけで修正する
- 再現せずに修正する
- 根本原因を特定せずに対症療法
- 試した内容を記録しない
- 同じ失敗を繰り返す
