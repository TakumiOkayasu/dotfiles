# Premise Questioning (そもそも論 - 戦略レベル)

着手直前の方針は、書いた本人には筋が良く見える。だが「そもそも解くべき問題か」「そもそもその実装は要るか」を一段引いて問い直すと、実装後にひっくり返ることがしょっちゅうある。**バイアスを排した実行者に違う角度から問いを立ててもらい、3 軸でスコア化して比較する**のが本 skill の核。最低 3 ラウンド、結論が割れている間は止めない。

**本 skill の責務範囲は「方針そのものの妥当性」まで**。「このページネーション要らない」「この保存ボタン要らない」級の機能粒度の指摘は別 skill (`feature-pruning`) で扱う。混ぜると単一責任が崩れる。

## いつ使うか

- 新規実装の着手直前 (設計が固まったが、コードはまだ書いていない段階)
- バグ修正の着手直前 (再現テスト前 / 修正方針を決めた直後)
- 設計判断のレビュー直前 (PR / MR 出す前のセルフチェック)
- 重要度の高い意思決定 (アーキテクチャ変更、外部依存追加、データ移行、技術選定など)

使わない場面:

- typo 修正 / コメント修正 / dependency bump など軽微な変更 (コストが割に合わない)
- 締切が迫って意思決定の余裕がないとき (止まる方が損失大。事後レビューで補う)
- 既に同等の skill (brainstorming-design など) を回した直後 (重複)
- **個別機能 / UI 要素の要否レビュー** → `feature-pruning` skill を使う

## ワークフロー

0. **対象方針の確定とパッケージ化**

   - 「これから実行しようとしている方針 / 実装案 / 修正案」を 1 段落 + 箇条書きで言語化する
   - 含めるもの: 解こうとしている問題 / 採用予定の方針 / 想定する影響範囲 / 既に検討して捨てた代替案 (あれば)
   - これが subagent への入力。曖昧だと判定も曖昧になる
1. **手法ローテートで 3 ラウンド dispatch**

   - **dispatch 主体は本 skill の発動主体 (親セッション。ユーザーと直接対話している Claude セッション)**。subagent から更に subagent を呼ぶ nested dispatch は Claude Code 標準 harness で許可されないため本 skill では要求しない (1 段の dispatch で完結する設計)
   - Round 1: **第一原理** (First Principles) - 最小単位まで分解し、再構築すると同じ方針になるか検証
   - Round 2: **Inversion** (逆思考) - 「この方針で失敗するとしたら何が原因か」を先に列挙し、致命的なものが現状方針で防げるか検証
   - Round 3: **5 Whys** - 解こうとしている問題に対し「なぜそれを解くのか」を 5 回連鎖させ、根本目的に対し本方針が最短経路か検証
   - **毎回新規 subagent を Task / Agent tool で dispatch** する (前回の出力を学習させない)。並列実行して構わない
   - dispatch 不能環境の扱いは「環境制約」節
2. **3 軸スコアリング** (各軸 0-5、判定文言は「スコア軸」節で一元定義)

   - subagent の自己申告で各軸採点 + 指示側で sanity check
3. **ラウンド間比較**
   - 3 ラウンド × 3 軸 = 9 セルを表形式で並べ、軸ごとのばらつきを見る
   - **結論ラベル**を付ける: ✅ 採用 / 🟡 修正必要 / 🔴 撤回検討
4. **収束判定** (詳細は「反復の打ち切り基準」節)

   - **判定主体は親 (本 skill 発動主体)**。subagent から返ってきた個別レポート (3 軸スコア / 結論ラベル / 結論根拠) を親が事後集約してから判定する。subagent は単一 Round 完結で「自分の Round の結論ラベル」のみ返し、ラウンド間集約・拡張モード発動判定は行わない
   - 3 ラウンド全 ✅ + 軸ばらつき ±1 以内 → 採用 (過適合チェック後)
   - 3 ラウンド全 🔴 + 軸ばらつき ±1 以内 → 撤回確定 (停止)
   - **🟡 単独一致**、または ✅/🟡/🔴 混在、または特定軸でばらつき 2 点以上 → Round 4 以降を追加 (拡張モード投入)
5. **結論アウトプット**

   - 採用なら「なぜ採用に値するか」の根拠 3 行
   - 修正必要なら「どの軸の何を改善すれば採用になるか」
   - 撤回検討なら「現方針の致命傷と、代わりに何を考えるべきか」
6. **次 skill への引き継ぎ**

   - 採用判定が出たら、機能リストが含まれる方針なら `feature-pruning` で機能粒度の検証に進むことを推奨

## 3 つの手法 (Core 3、ラウンドごとにローテート)

### Round 1: 第一原理 (First Principles)

問い: 「この問題を一切の慣習・既存実装・チーム慣行抜きで考えたら、最小構成は何か。現状方針はその最小構成からどれだけ離れているか」

検出しやすい問題:

- 既存実装の慣性で過剰な複雑さが入っている
- 「うちでは昔からこうしている」由来の不要な層
- ライブラリ選定が問題に対しオーバースペック

弱点: 既存資産との整合性 (移行コスト) を見落としがち

### Round 2: Inversion (逆思考)

問い: 「この方針が 3 ヶ月後に失敗していると仮定する。最も可能性の高い失敗シナリオを 5 つ列挙し、現状方針でそれぞれ防げるか判定せよ」

検出しやすい問題:

- 隠れた前提 (「○○は変わらない」「××は壊れない」) の脆弱性
- 運用フェーズの考慮漏れ
- エラー / 障害時の振る舞い未定義

弱点: 失敗シナリオが想像力依存。スコア「仮定健全性」で重点配分

### Round 3: 5 Whys

問い: 「解こうとしている問題に対し『なぜ解くのか』を 5 回連鎖させよ。最終 Why から見て、本方針はその目的に対する最短経路か。より短い経路はないか」

検出しやすい問題:

- 真の目的を達成しない / 副次効果しか狙えていない方針
- 「問題の症状」を直しているが「原因」を残している
- 別レイヤーで解くべき問題を、現レイヤーで力技で解こうとしている

弱点: Why の連鎖が誘導的になりがち (subagent の自由度を確保するため、最初の Why を指示側で書かない)

### 拡張モード (Round 4 以降で発動)

**発動判定は親 (本 skill 発動主体)**。subagent は単一 Round 完結のため、3 ラウンド集約後に親が以下のいずれかを検出した場合に Round 4-5 として追加 dispatch する:

- 結論ラベルがラウンド間で割れる (✅ / 🟡 / 🔴 混在)
- **🟡 単独一致** (修正必要のみで揃った場合。「採用」にも「撤回」にも該当しないため追加検討が必要)
- 特定軸でラウンド間ばらつきが 2 点以上

追加投入する手法:

- **制約除去** - 「予算 / 工数 / 既存資産 / 互換性の制約を全部外したら、何を選ぶか」。現状方針との差分が、制約由来か本質由来かを切り分ける
- **問題再定義** - 「問題文を書き直すならどう書くか。現状の問題文は症状か、原因か、目的か」

## 採点根拠の引用形式

各軸の採点根拠は **(a) 必須 / (b) 併記推奨** の 2 行で書く (判定の追跡可能性のため):

- (a) 判定文言引用 **(必須)**: 下記「スコア軸」節の該当点の文言を逐語引用する (例: 「Q-Val=1: 問題として成立しているか怪しい (実害が薄い、自然解消が見込める)」)
- (b) 数値根拠 **(具体数値が出せる場合は必須)**: 推定使用率 / 暗黙仮定数 / 影響範囲 等の具体値で示す (例: 「Q-Val=3: 推定使用率 30%、月間 2-3 件発生、後回し許容」)

(b) を「具体数値が出せない」と省略する場合、採点が判定文言からの推測に留まっている可能性が高く、**再 dispatch 案件**。抽象表現 (「重要そう」「便利そう」「重要度が高そう」) は NG。subagent レポートで全 3 軸の採点根拠がこの形式で書かれていない場合は再 dispatch する。

## スコア軸 (判定文言の一元定義)

「軸名から推測した採点は判定文言に届かない」(empirical の教訓)。各点の判定基準を文言レベルで固定する。

### Q-Validity (問題妥当性)

- 5: その問題はビジネス / ユーザー価値に直結し、解かないと顕著な悪影響がある
- 4: 価値に直結するが、現状の運用回避で 1 サイクルは凌げる (恒久対処は必要)
- 3: 解いた方がいいが、優先度は中程度。後回しにしても致命的ではない
- 2: 一部ユーザーの不便があるが、放置しても主要動線には影響しない
- 1: 問題として成立しているか怪しい (実害が薄い、自然解消が見込める)
- 0: 上位の問題でカバーされる / そもそも要件解釈が誤っている

### S-Necessity (解決策必要性)

- 5: この実装 / 修正なしには問題が解けない (代替手段なし)
- 4: 実装が最短経路だが、設定 / 運用回避にも 1 段階の追加コストで到達可能
- 3: 他の手段でも解けるが、現状方針が現実的にバランスが良い
- 2: 部分的に必要、半分以上は設定 / 運用で代替できる
- 1: 設定変更 / ドキュメント追記 / 運用回避で済む可能性が高い
- 0: 実装すること自体が overengineering、不要

### A-Soundness (仮定健全性)

- 5: 依存する前提が全て明文化済みで、崩れる確率も影響も低い
- 4: 暗黙仮定が 1 個あるが影響は局所的、検出も容易 (テスト / ログで顕在化)
- 3: 前提に 1-2 個の暗黙仮定があるが、崩れても局所影響に収まる
- 2: 暗黙仮定が複数あるが、いずれも検出時点で局所修正可能
- 1: 重要な暗黙仮定があり、崩れると広範囲に影響する
- 0: 前提が確認されていない / 既に怪しい (外部 API の挙動仮定など)

### 重み付け

質的 (代替方針の中身、結論根拠) を主、量的 (3 軸合計点) を補助とする。**合計点が高くても、1 軸でも 1 以下があれば 🔴 撤回検討に倒す** (致命傷の隠蔽防止)。

## 環境制約

新規 subagent を dispatch できない環境では本 skill は **適用しない**。**dispatch 主体は親セッション (ユーザー直結の Claude セッション) に限定**。subagent が更に subagent を呼ぶ nested dispatch は本 skill では要求しない (Claude Code 標準 harness で 1 段制限あり)。

判定方法: 親セッションの利用可能 tool に `Task` / `Agent` tool (新規 LLM コンテキストを起動する dispatch tool) が含まれるかを確認。`TaskCreate` / `TaskList` (session 内 todo 管理) や `RemoteTrigger` / `CronCreate` (非同期スケジュール) は dispatch tool ではないため適用不可判定の対象。

- 代替案 1: 親セッションのユーザーに別 Claude Code セッションでの確認を依頼
- 代替案 2: スキップを明示報告 (「premise-questioning skipped: dispatch unavailable」)
- **NG**: 自分で 3 手法を順に当てて自己評価する (バイアス排除の構造が崩れるので結果を信じてはいけない)

**簡易モード**: 重要度が低い意思決定で軽く回したい場合は、**1 ラウンド (第一原理のみ) + 自己採点** に縮退。ただし「3 ラウンドで採点した」とは言わない (混同回避)。

- **簡易モード時の過適合チェック (hold-out)**: 不要。下記「反復の打ち切り基準」節の過適合チェックは 3 ラウンド全 ✅ 採用判定後の手順であり、1 ラウンドのみの簡易モードは対象外。簡易モードで結論に確信が持てない場合は通常モード (3 ラウンド) に切り替えて再評価する

## 反復の打ち切り基準

- **収束 (採用 / 撤回どちらでも停止)**:
   - 3 ラウンド全てで結論ラベルが一致 (**全 ✅ または全 🔴 のみ**。**🟡 単独一致は収束扱いではなく追加ラウンド発動**: 修正必要は採用にも撤回にもならず追加検討が要る)
   - かつ各軸のラウンド間ばらつきが ±1 点以内
- **追加ラウンド発動**:
   - 結論ラベルがラウンド間で割れる (例: ✅ / 🟡 / 🔴 が混在)
   - または 🟡 単独一致
   - または特定軸でラウンド間ばらつきが 2 点以上
   - → 拡張モード (制約除去 / 問題再定義) を Round 4-5 として追加投入。**発動判定は親 (本 skill 発動主体) が事後集約後に行う**
- **発散 (設計を疑う)**:
   - 5 ラウンド回しても結論が割れ続ける → そもそも対象方針が複雑すぎて「そもそも論」では捌けない。問題を分解して各部分に対して個別に再適用する
- **過適合チェック (通常モードのみ)**:
   - **適用条件**: 通常モード (3 ラウンド) で全 ✅ 採用判定が出た直後のみ。簡易モード (1 ラウンド) や 🔴 撤回判定 / 🟡 単独一致時は対象外
   - **手順**: hold-out として「現状方針と真逆の方針」を仮置きして 1 ラウンド回す。それでも対象方針が勝つなら採用確定、負けるなら判定を疑う

## Red flags (合理化に注意)

| 出てくる合理化 | 実態 |
| --- | --- |
| 「自分で 3 つの視点を順に考えれば dispatch 不要」 | 直前に書いた方針を客観視はできない (empirical の核と同じ問題)。dispatch 必須 |
| 「1 ラウンドで充分、結論一致してる」 | 1 手法は盲点が手法と紐付いて固定。最低 3、できれば手法違いで |
| 「採用ラベル 1 回出たから着手」 | 偶然なこともある。3 ラウンドの一致で確定 |
| 「合計点高いから採用」 | 1 軸でも 1 以下があれば致命傷の可能性。最低点軸を主に見る |
| 「結論が割れたから多数決で決める」 | 多数決は「そもそも論」で最も避けるべき。割れる = 拡張ラウンド発動の合図 |
| 「軸名で採点、判定文言は読まなくていい」 | 採点が軸名から推測になり判定文言に届かない (empirical の修正の波及パターンと同じ罠) |
| 「同じ subagent を使い回そう」 | 前ラウンドの結論を引きずる。毎ラウンド新規 dispatch |
| 「機能粒度の指摘もここでやる」 | 単一責任違反。機能粒度は feature-pruning に委譲 |
| 「採用後の hold-out 省略」 | 3 ラウンド全 ✅ で気が緩む。逆方針 1 ラウンドの手間を惜しまない |

## よくある失敗

- **対象方針のパッケージが薄すぎる**: 「○○を実装したい」だけでは subagent も判定できない。問題 / 方針 / 影響範囲 / 検討済み代替案を最低限揃える
- **結論が割れたのを「多角的に検討された」と肯定的に解釈**: 割れている時点で根拠が弱い。追加ラウンドで詰める
- **採用判定後の hold-out チェックを省略**: 3 ラウンドで全 ✅ が出ると気持ちよくなって過適合を見逃す。逆方針を 1 ラウンドだけ回す手間を惜しまない
- **手法を恣意的に省略**: 「Inversion はピンと来ないから 5 Whys で 2 回回そう」は手法の盲点固定。Core 3 は 1 回ずつ必須
- **修正必要 (🟡) を「ほぼ ✅」と読み替え**: 🟡 は「修正なしには採用しない」のラベル。修正してから再ラウンドが正解
- **責務範囲外まで踏み込む**: 「ついでに機能リストの要否も…」は本 skill ではやらない。`feature-pruning` で別途回す

## 関連 skill

- `empirical-prompt-tuning` - 本 skill のバイアス排除手法 (subagent dispatch / 連続クリア判定 / 過適合チェック) はここから踏襲
- `feature-pruning` - **本 skill の戦術版**。本 skill で方針が採用判定された後、機能リストが含まれる方針なら次にこちらを回す。役割分担: 本 skill = 戦略 (方針自体)、feature-pruning = 戦術 (個別機能)
- `brainstorming-design` - 着手前のアイデア発散。順序: brainstorming → premise-questioning → (機能リストあれば) feature-pruning → 着手
- `systematic-debugging` - バグ修正時、根本原因分析と併用可。systematic-debugging で原因特定 → premise-questioning で「修正方針が筋が良いか」を問う流れ
- `interface-composition-design` - 設計判断時に併用可
