# Test Coverage Guard

## 目的

**テストの偽陽性を防ぎ、テストスイート全体の信頼性と網羅性を保証する。**

偽陽性 = 本来FAILすべきテストがPASSしている状態。テストスイートが緑でも本番で壊れるなら、そのテストは誤った安心感を与えるだけで害。

検証領域: (1) 偽陽性パターンの検出 (2) 異常系・境界値・セキュリティ・並行性の網羅性 (3) テスト品質・安定性の確保

### test-driven-developmentスキルとの責務分担

| 責務 | TDDスキル | 本スキル |
|------|----------|---------|
| TDDサイクル(RED-GREEN-REFACTOR) | ◎ 主担当 | - |
| テストリスト作成・命名規則 | ◎ 主担当 | 検証(規則準拠か) |
| テスト粒度の選択・テストトロフィー | ◎ 主担当 | - |
| 偽陽性パターンの検出 | - | ◎ 主担当 |
| 異常系・境界値の網羅性検証 | - | ◎ 主担当 |
| セキュリティ・並行性テストの要否判断 | - | ◎ 主担当 |
| モック戦略の妥当性検証 | - | ◎ 主担当 |

**判断が矛盾した場合**: 本スキルが優先。TDDサイクルで書いたテストでも、本スキルの検証に通らないなら書き直す。

### 連携フロー

```
[TDDスキル] テストリスト → テスト名決定 → RED-GREEN-REFACTOR
    ↓
[本スキル] 信頼性検証(偽陽性チェック、網羅性検証)
    ↓
不足があれば → [TDDスキル] に戻ってテスト追加
```

## テスト信頼性の3原則

1. **呼び出し文脈を再現せよ** — 実際の呼び出し状況(前後の処理、データ状態、依存関係)を再現していないテストは偽陽性リスクを持つ
2. **粒度は検証したい振る舞いで決めよ** — 「テストしやすいから」で粒度を選ばない。副作用を含む振る舞いなら副作用を含むレベルでテストする
3. **正常系は半分でしかない** — 異常系・エラーパス・境界値・不正入力のテストがなければ半分しかカバーしていない

## 偽陽性パターン集

テストを書いたら、以下に該当しないか**すべて**確認する。

| # | パターン | 説明 | 該当しやすい場面 |
|---|---------|------|----------------|
| 1 | 呼び出し文脈の欠落 | 「理想状態」でのみ実行し、前後の処理がデータ状態を変えることを再現していない | バッチ処理、パイプライン、ミドルウェアチェーン |
| 2 | privateの直接テスト | Reflection/`_name`直接アクセス等でprivateを直接テスト。前段のvalidation・状態変更が通らず危険。public経由に書き換える | 例外: 統合テスト済+純粋計算+境界値網羅困難+抽出不適切の全条件を満たす場合のみ許可 |
| 3 | モック過多 | 依存をほぼすべてモック化し「モック間の配線」だけをテスト。外部APIのみモック、DBは実物を使い実際の状態を検証する | サービスクラスの単体テスト |
| 4 | テストデータの手動構築 | Fixture/Factoryで「理想状態」のデータを手動作成し、実フローで生成されるデータと構造が異なる。可能な限り実際の操作フローでデータを作成する | マスタ系テスト |
| 5 | 環境・タイミング依存 | 結果がシステム時刻・実行順序・ネットワーク状態に依存。非決定的な値は注入可能にする | 日時処理、外部API呼び出し |
| 6 | アサーション不足 | 「例外が出ない」ことだけを検証。**ミューテーション思考実験**: コアロジック削除/反転でFAILしなければアサーション不足(equivalent mutant除く) | ハッピーパスのみのテスト |
| 7 | スナップショットの形骸化 | 差分が出るたびに内容未確認で更新。差分レビュー可能なサイズに保ち、構造的に重要な部分は明示的にアサートする | UI/シリアライズテスト |
| 8 | テスト用DBと本番DBの挙動差異 | テストでSQLite、本番でPostgreSQL等。差異: JSON型、日付関数、UPSERT、型厳密性、トランザクション分離、LIKE大文字小文字。Testcontainersで本番と同じDBを使う | DB依存テスト全般 |

## 網羅性検証

### 異常系テスト

すべての機能に対して以下を確認する。

- **入力の異常**: null/空文字/空配列、最大長超過、マルチバイト/制御文字、0/負数/NaN/Infinity、空配列/大量/重複、不正日付/タイムゾーン境界、存在しないID/削除済みID
- **状態の異常**: 未認証/権限不足/トークン期限切れ、論理削除済み/処理中ロック/完了済み再実行、楽観ロック競合/同時更新、タイムアウト/接続エラー/不正レスポンス
- **エラーレスポンス品質**: エラーの種類・メッセージ・ステータスコード・副作用の不在まで検証する

### 境界値テスト

「ちょうど境界」「境界-1」「境界+1」の3点セットでテストする。見落としやすい例: 文字列長(0,1,最大,最大+1)、ページネーション(0件,ちょうど1ページ,+1)、日付範囲(開始=終了,月末月初)、金額(0円,小数丸め,割引で0以下)。手動で漏れる場合はProperty-Based Testing(fast-check, Hypothesis等)で補強する。

### セキュリティテスト

認証・認可・ユーザー入力を扱う機能で通常テストスイートに含める。対象: SQLインジェクション、XSS(出力エスケープ)、認証バイパス(未認証/期限切れ)、認可バイパス(他ユーザーリソース+副作用不在も検証)、CSRF(トークンなし状態変更)、マスアサインメント(更新不可フィールド上書き)。

### 並行性テスト

データ整合性が重要なシステムで検証する。対象: 同一リソース同時更新(ロック動作)、同時減算(マイナス防止)、二重送信(冪等性)、同時登録(一意制約)、デッドロック(検出・リトライ)、Read/Write Skew(分離レベル整合性)。

## モック使用の検証基準

| 判定 | 対象 | 理由 |
|------|------|------|
| 妥当 | 外部API(決済,SMS,メール等) | 課金発生、副作用不可逆、レート制限 |
| 妥当 | 非決定的な値(時刻,乱数,UUID) | 再現性確保 |
| 妥当 | 障害シミュレーション(タイムアウト,503等) | 正常系では発生不可 |
| 避ける | 自プロジェクトのDB | テスト用DB(Testcontainers推奨)を使う |
| 避ける | 自プロジェクトの他クラス/モジュール | 実物を使った統合テスト |
| 避ける | ファイルシステム | tmpディレクトリでの実操作 |

**モック使用時のルール**: (1) 戻り値を実レスポンス構造(型、フィールド名、ネスト)と一致させる (2) エラーケースもモックする (3) 対象が外部境界かで判断(数ではなく性質) (4) 重要な外部連携では契約テスト(Pact等)を検討する

## テストレビューチェックリスト

テストを書いたら以下で自己レビューする。

**偽陽性防止(毎回)**:

- [ ] 実際の呼び出し文脈(前処理の副作用含む)を再現しているか?
- [ ] コアロジック削除/反転でFAILするか?(equivalent mutant除外)
- [ ] private相当を言語固有の仕組みで直接テストしていないか?
- [ ] 副作用を伴う処理を単体テストだけで完了としていないか?
- [ ] 「例外が出ない」だけのテストになっていないか?
- [ ] テスト名から「対象」「条件」「期待結果」が読み取れるか?

**網羅性(機能追加・変更時)**:

- [ ] 正常系 + 異常系(不正入力、認証エラー、リソース不在等)があるか?
- [ ] 境界値(境界, -1, +1)があるか?
- [ ] エラーレスポンスの品質(型、メッセージ、ステータスコード)と副作用の不在を検証しているか?

**セキュリティ(認証・認可・ユーザー入力を扱う場合)**:

- [ ] 未認証・他ユーザーリソースへのアクセス拒否テストがあるか?
- [ ] 入力のエスケープ・更新不可フィールドの上書き防止テストがあるか?

**モック(モック使用時)**:

- [ ] モック対象はすべて外部境界か?
- [ ] モックの戻り値は実レスポンスと構造一致しているか?
- [ ] モックのエラーケースもテストしているか?

**安定性(CI/フレイキー対策)**:

- [ ] 実行順序・システム時刻・ネットワークに依存していないか?
- [ ] 並列実行しても安全か?
- [ ] テストごとにDB/ファイル/キャッシュ等の状態をリセットしているか?(setUp/tearDown)
- [ ] グローバル変数・シングルトン・static変数をテスト間で共有していないか?

**DB(DB使用テスト)**:

- [ ] テスト用DBと本番DBのエンジン差異を認識しているか?

**回帰(バグ修正時)**:

- [ ] バグを再現するテストが修正前にFAILすることを確認したか?

**特性テスト(存在する場合)**:

- [ ] `CHARACTERIZATION:`プレフィックスがあるか?
- [ ] 長期放置(目安3ヶ月)されていないか? → 昇格・修正・削除を判断

## 運用ガイドライン

### フレイキーテスト対策

放置禁止。検出(直近N回中2回以上結果が異なる) → 隔離(`@Flaky`タグ、メインCIから除外) → 期限内に修正 → 復帰または安定版テスト新規作成後に削除。よくある原因: テスト間の状態共有、非同期処理の待機不足(sleep固定値→ポーリング)、外部サービス依存、共有リソース競合、システム時刻依存、auto-increment ID依存。

### テストの削除基準

価値を失ったテストは削除する。カバレッジ数値のために形骸化テストを維持するのは害。削除対象: 常にPASSするテスト(アサーションなし/トートロジー)、実装内部をなぞるだけのテスト、同じ振る舞いの重複テスト、モック過多で実振る舞い未検証のテスト、修正見込みのないフレイキーテスト。削除前に代替テストの有無とリライト可能性を確認する。

### カバレッジの正しい使い方

カバレッジ数値は目標ではなくテスト漏れの検出指標。ラインカバレッジよりブランチカバレッジ(分岐網羅)を重視する。uncovered branches表示で漏れを発見する用途に限定し、数値目標化しない。

### 副作用の定義

以下のいずれかを行う処理を「副作用あり」とみなし統合テスト以上で検証する: DB書き込み、DB読み取り(トランザクション分離・読み取り整合性が要件の場合)、ファイルシステム読み書き、外部APIリクエスト、キャッシュ読み書き、セッション/Cookie変更、メッセージキューpublish/consume、イベント発行。ログ出力は内容の正確性が要件でない限りテスト不要。
