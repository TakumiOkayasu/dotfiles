# Test Coverage Guard

## トリガー条件

以下のキーワード・状況で発動する:

**キーワード**
- 「テストレビュー」「テストの品質」「テストが信頼できない」「偽陽性」「false positive」
- 「テストは通るのに本番で壊れる」「モックが多すぎる」「テストダブル過多」
- 「カバレッジは高いのにバグが出る」「フレイキーテスト」「flaky test」
- 「テスト削除していい?」「このテスト意味ある?」「テストの網羅性」「テストのレビューして」
- 「test review」「test quality」「mutation testing」「ミューテーションテスト」
- 「テストスイートが通っているのに不安」「既存テストの品質を上げたい」「テスト全部通るけど大丈夫?」

**状況**
- テストがGREENになった後、テストスイートの品質に不安がある場面
- PRレビューでテストコードの品質を確認したい場合

**非対象**（他スキルへ委譲）
- テストを新規に書く作業 → `test-driven-development`
- CI/CDパイプラインの設定 → `ci-cd`
- セキュリティテストの詳細設計 → `security-review`

---

## 前提条件

- レビュー対象のテストファイルが存在すること
- テストが実行可能な状態であること（環境構築済み）
- 対象プロジェクトの言語・テストフレームワークが判明していること

---

## 目的

テストの偽陽性を検出・排除し、テストスイートの信頼性を保証する。

**偽陽性**: 本来FAILすべきテストがPASSしている状態。テストスイートが緑でも本番で壊れるなら、そのテストは誤った安心感を与えるだけであり、保守コストの分だけマイナスになる。

### test-driven-developmentスキルとの責務分離

| スキル | 責務 | タイミング |
|--------|------|-----------|
| **test-driven-development** | テストの設計・作成（TDDサイクル、テストリスト、テスト名規約、AAA構造） | テストを書く時 |
| **本スキル** | テストの検証（偽陽性検出、アサーション品質、テストダブル妥当性、網羅性の指摘） | テストがGREENになった後 |

本スキルはTDDサイクルを中断・上書きしない。不足が見つかったら「何が不足しているか」を報告し、テストケースの追加はTDDスキルに委譲する。

## 実行手順

### Step 1: スコープ特定

レビュー対象を決定する。対象が不明確な場合はユーザーに確認する。

| 戦略 | 適用場面 | やること |
|------|---------|---------|
| **PR差分ベース** | PRレビュー、直近の変更 | 変更されたテストファイル＋変更されたプロダクションコードに対応するテストファイル |
| **モジュール単位** | 「この機能のテストをレビューして」 | 指定モジュールのテストディレクトリ配下 |
| **リスクベース** | テストスイート全体の品質確認 | カバレッジが低い箇所、最近バグが出た箇所、ビジネスクリティカルな機能を優先 |
| **全件** | 小規模プロジェクト、初回導入 | テストスイート全体 |

> ⚠️ 大規模プロジェクトで対象が100件を超える場合、リスクベースで絞り込みを提案する。

---

### Step 2: 偽陽性スキャン（優先度順）

以下のパターンを **P1→P2→P3** の順に確認する。

#### P1（即時修正）: テストが実質的に何も検証していない

**パターン1: アサーション不足**

テストが「例外が出ない」ことだけを検証しており、戻り値・状態変化・副作用を検証していない。

検出方法: テスト対象のコアロジックを `return null` に置換したと想像する。それでもPASSするならアサーション不足が確定。

```pseudo
// NG: 実行しただけ
test "processOrder works":
    service.processOrder(order)
    // アサーションなし → return null にしてもPASS

// OK: 戻り値 + 状態変化 + 副作用を検証
test "processOrder sets status to processed and saves":
    result = service.processOrder(order)
    assert result.status == "processed"
    assert result.processedAt != null
    saved = db.find(Order, order.id)
    assert saved.status == "processed"
```

**パターン2: テストダブル過多**

テスト対象の依存をほぼすべて差し替えており、テストしているのは「配線の確認」だけになっている。

```pseudo
// NG: 4つのMock、呼び出し検証のみ
test "OrderService.place creates order":
    mockRepo = mock(OrderRepository)
    mockPayment = mock(PaymentGateway)
    mockInventory = mock(InventoryService)
    mockNotifier = mock(Notifier)
    service = new OrderService(mockRepo, mockPayment, mockInventory, mockNotifier)
    service.place(order)
    assert mockRepo.save.calledOnce  // 配線しか見ていない

// OK: 外部APIのみStub、DBは実物で状態を検証
test "OrderService.place creates order":
    stubPayment = stub(PaymentGateway, charge: success)
    service = new OrderService(realRepo, stubPayment, realInventory, realNotifier)
    service.place(order)
    saved = db.find(Order, order.id)
    assert saved.status == "confirmed"
```

判断基準: Mock（呼び出し検証）が2つ以上で要注意。テストダブル合計が5つ以上なら設計自体の見直しを検討。

**パターン3: 呼び出し文脈の欠落**

テスト対象を「理想状態」で実行しており、実際のフローで前後の処理がデータ状態を変えることが再現されていない。

```pseudo
// NG: processItemだけを理想状態でテスト
test "processItem returns correct result":
    item = createTestItem(status: "active")
    result = processItem(item)
    assert result.value == expected

// OK: 実際のフロー（前処理がstatusを変えうる）を再現
test "processItem works after preprocessing":
    item = createTestItem(status: "active")
    preprocessor.run(item)  // 本番では必ず通る前処理
    result = processItem(item)
    assert result.value == expected
```

該当しやすい場面: バッチ処理のステップ、パイプライン、ミドルウェアチェーン。

**パターン4: privateメソッドの直接テスト**

Reflection/friend/InternalsVisibleTo等でprivateメソッドを直接テストしている。privateメソッドの前に実行されるvalidation・状態変更が一切通らないため、本番の実行パスと乖離する。publicメソッド経由の間接検証に置き換える。

例外条件（以下の**すべて**を満たす場合のみ許可）:
1. 同じ機能の統合テストが既に存在しPASSしている
2. テスト対象が純粋な計算ロジック（副作用なし）
3. 統合テストでは網羅が困難な境界値テスト
4. 別関数/メソッドへの抽出を検討した上で、抽出が不適切と判断した理由をコメントで明記している

#### P2（次スプリント）: カバー範囲の不足

**パターン5: 正常系のみ**

Happy Pathのテストしかなく、エラーパス・不正入力・境界値のテストが存在しない。

不足を特定する観点:
- **入力の異常**: null/undefined/空文字、0/負数/最大値、存在しないID/削除済みID
- **状態の異常**: 未認証、権限不足、論理削除済み、ロック中、完了済み操作の再実行
- **外部依存の異常**: タイムアウト、接続エラー、不正レスポンス、レート制限
- **境界値**: 「ちょうど境界」「境界-1」「境界+1」の3点セット

> 本スキルでは「これらのテストが存在しない」ことを指摘する。テストの追加自体はTDDスキルに委譲する。

#### P3（バックログ）: 信頼性・安定性への影響

**パターン6: テストデータと本番データの乖離**

Factory/Fixtureで作成したデータが、実際のデータフローで生成されるデータと構造的に異なる。

乖離が起きやすいケース:
- 本番ではDB側のデフォルト値・トリガーがフィールドを埋めるが、Factoryでは再現していない
- 本番では前処理（バリデーション、正規化）を経てデータが作られるが、Factoryでは加工済みデータを直接セット
- 本番では関連テーブルが連動して作られるが、Factoryでは対象テーブルだけ作成

対策: 重要なテストデータは本番と同じAPI/サービス経由で作成する。

**パターン7: 環境・タイミング依存（フレイキーの温床）**

| 原因 | 対策 |
|------|------|
| テスト間の状態共有 | テストごとにDB/状態をリセット |
| 非同期の待機不足 | ポーリングアサーション（waitFor, eventually）。`sleep(固定値)` は禁止 |
| 外部サービス依存 | テストダブルまたはテストコンテナに切り替え |
| システム時刻依存 | FakeClockで時刻を注入可能にする |
| 並列実行時のリソース競合 | テストごとにスキーマ分離またはトランザクション分離 |

> ⚠️ フレイキーテストは放置禁止。修正するか削除する。

**パターン8: スナップショットの形骸化**

差分が出るたびに内容を確認せず `--update-snapshot` している。スナップショットは50行以下に保ち、構造的に重要な部分は別途明示的にアサートする。

### Step 3: ミューテーション思考実験

Step 2で問題なしと判断されたテストに対し、「このテストは本当にバグを検出できるか?」を検証する。

以下の変異を**思考上で**適用し、1つでもFAILしなければアサーション不足:

1. コアロジックを `return null` に置換 → FAILするか?
2. if条件を反転 → FAILするか?
3. 演算子を変更（`+`→`-`、`>`→`>=`） → FAILするか?
4. 重要な副作用（DB保存、通知送信）をコメントアウト → FAILするか?

ミューテーションスコア（検出できたミュータントの割合）はカバレッジ数値よりテスト品質の指標として信頼性が高い。目安80%以上を推奨するが、等価ミュータントがあるため100%は不要。

ツールで自動化する場合:

| 言語 | ツール | 言語 | ツール |
|------|--------|------|--------|
| JS/TS | Stryker | Python | mutmut |
| Java/Kotlin | PIT | Ruby | mutant |
| PHP | Infection | Rust | cargo-mutants |
| Go | gremlins, ooze | C#/.NET | Stryker.NET |

### Step 4: テストダブル検証

テストダブルを使用しているテストに対して以下を確認する。

**チェックポイント**

1. **Mock数**: 1テストあたり2つ以上で要注意
2. **レスポンスの一致**: 型・フィールド名・ネスト構造が実際のレスポンスと一致しているか
3. **エラーケース**: タイムアウト・エラーレスポンス・不正データのStubも存在するか
4. **自プロジェクトのDB/クラスをテストダブルで差し替えていないか**: 実物を使うのが原則

**テストダブルの種類と使い分け**

| 種類 | 目的 | 推奨用途 |
|------|------|---------|
| **Stub** | 固定値を返す（入力制御） | 外部APIの正常/異常レスポンス |
| **Mock** | 呼び出しを検証する（出力検証） | 通知送信など副作用の発生確認 |
| **Fake** | 簡易実装（本物に近い振る舞い） | InMemoryRepository, FakeClock |
| **Spy** | 実物＋呼び出し記録 | 実処理を維持しつつログ等を記録 |

**何をテストダブルにすべきか**

| 対象 | 推奨 | 理由 |
|------|------|------|
| 外部API（決済, SMS等） | Stub/Mock | 課金発生、副作用が不可逆 |
| 非決定的な値（時刻, 乱数） | Fake | テストの再現性確保 |
| 障害シミュレーション | Stub | 正常系では発生させられない |
| 自プロジェクトのDB | **実物** | テストダブルとの振る舞い乖離が大きい |
| 自プロジェクトの他クラス | **実物** | 連携の検証ができない |

**Contract Testの検討**

| 条件 | 推奨アプローチ |
|------|--------------|
| マイクロサービス間通信で提供側と利用側が別チーム | Consumer-Driven（Pact） |
| 外部APIのStubをAPI仕様変更で壊れた経験がある | Provider-Driven（OpenAPI + Prism） |

> 導入コストが高いため、Stubの乖離で実際に問題が起きた実績がある場合に限定する。

### Step 5: 網羅性の指摘

正常系テストに対応する異常系・境界値テストの有無を確認する。

確認観点:
- 正常系テストがある機能に、対応する異常系テストが存在するか
- エラーレスポンスの品質（型・メッセージ・ステータス）と副作用の不在を検証しているか
- セキュリティ関連（未認証拒否、他ユーザーのリソースへのアクセス拒否）のテストが存在するか
- 並行性が関係する場合（楽観ロック、在庫の同時減算、冪等性）のテストが存在するか

```pseudo
// NG: エラーが出ることだけ確認
assertThrows(() => service.process(invalidInput))

// OK: エラーの型・メッセージ + 副作用の不在
error = assertThrows(() => service.process(invalidInput))
assert error.type == ValidationError
assert error.statusCode == 422
assert db.count(ProcessedItem) == originalCount  // 副作用が発生していない
```

不足テストの一覧をレポートに含める。テストの設計・実装はTDDスキルに委譲する。

> 境界値の網羅的な探索にはProperty-Based Testingが有効（JS/TS: fast-check、Python: Hypothesis、Java/Kotlin: jqwik、Rust: proptest）。PBTは既存の例示テストを**置き換えるものではなく補完するもの**。

## 禁止事項・制約

| 禁止事項 | 理由 |
|---------|------|
| 不足テストを本スキル内で実装する | テスト作成はTDDスキルの責務 |
| TDDサイクルを中断・上書きする | 本スキルは検証専用 |
| `sleep(固定値)` による非同期待機 | フレイキーの原因 |
| フレイキーテストの放置 | CI全体の信頼性を下げる |
| カバレッジ数値を目標として追う | 価値の低いテストを量産する |
| 既存コードへカバレッジゲートを遡及適用 | 価値の低いテストを量産するインセンティブが生まれる |

## テスト削除の判断基準

### 削除してよい条件

以下の**いずれか**に該当し、**かつ**同等以上の検証を行う代替テストがある（または追加する）場合のみ:

1. 同層の他テストと検証内容が完全に重複しており、独自に検出できるバグがない
2. 過去6ヶ月でリファクタリング起因の修正が3回以上発生し、その間バグを1度も検出していない
3. テストダブルの保守コストが、テストが検出するリスクに見合わない

### 即削除すべきテスト

| テスト | 理由 |
|--------|------|
| 常にPASSする（アサーションなし/トートロジー） | 偽の安心感 |
| 実装の内部構造をそのままなぞっている | リファクタリングのたびに壊れる |
| テストダブル過多で実際の振る舞いを検証していない | 偽陽性の温床 |
| フレイキーで修正見込みなし | CI全体の信頼性を下げる |

> 削除前に確認: 代替テストの有無、リライトで改善可能か。

## カバレッジの正しい使い方

カバレッジ数値は目標ではなく、テスト漏れの発見ツール。

高カバレッジでも信頼できないケース: アサーションなしで行を通過、正常系だけで100%到達、テストダブルで差し替えた部分を計上。

推奨:
- ラインカバレッジよりブランチカバレッジを重視する
- ミューテーションスコアを併用するとテストの検出力を直接計測できる
- カバレッジのCIゲートは「新規コード/変更コード」に限定する
- カバレッジレポートの「未カバー行」をテスト追加の候補リストとして使う

## 関連スキルとの連携

| スキル | 連携ポイント |
|--------|------------|
| **test-driven-development** | 不足が見つかったらTDDスキルに戻ってテストケースを追加。本スキルは指摘まで |
| **ci-cd** | テストの段階実行、CIゲート（カバレッジ閾値等）の設定 |
| **security-review** | セキュリティテストの詳細設計 |
| **code-review** | テストコードのレビュー観点 |
| **performance-optimization** | テスト実行時間のボトルネック調査 |
