直近の変更を**多角的に**レビューする。セキュリティ・パフォーマンス・保守性の 3 観点を並列で検査し、優先度順に統合する。

`$ARGUMENTS` にレビュー対象を指定（省略時は直近の変更）。

## トリガー語 (自動委譲用)

- 「多角的なコードレビュー」「並列レビュー」「deep review」
- 「セキュリティ・パフォーマンス・保守性をまとめてチェック」
- 「3 視点でレビュー」「観点別レビュー」
- `/code-review` 直接起動

## 入力

| 入力元 | 内容 |
|--------|------|
| `$ARGUMENTS` | ブランチ名・コミットハッシュ・ファイルパス等（省略可） |
| `git diff` | ステージ済み＋未ステージの差分 |
| `CLAUDE.md` / `.claude/rules/` / `~/.claude/rules/` | プロジェクト規約 |

## 出力

| 出力項目 | 内容 |
|----------|------|
| 判定ヘッダー | `BLOCK` / `WARN` / `PASS` |
| サマリー表 | Critical / Warning / Suggestion 件数 |
| 統合済み指摘リスト | 重要度順・file:line + 観点タグ + 修正案 |

## 鉄則

- **全指摘に修正コードを添える。修正案なき指摘は指摘ではない。**
- **3 並列 subagent の結果を統合して 1 つの優先度順リストに集約する。**

---

## 並列編集警告 (将来拡張への布石)

本 command は read-only (差分閲覧のみ) だが、将来 subagent に修正提案実装まで委譲する場合は **同一ファイルへの並列編集を禁止** する。修正実装フェーズでは subagent を直列実行するか、ファイル所有を分割すること。

---

## レビュー手順

### Step 1: 差分取得

```bash
# $ARGUMENTS が指定されている場合はそれを使用
# 省略時は以下を順に試行:
# 1. git diff HEAD        （ステージ済み＋未ステージの変更）
# 2. git diff HEAD~1      （直近コミットの変更）
```

### Step 2: 全体把握

1. 変更の目的・スコープを理解する
2. 影響範囲を特定する
3. 変更ファイルの import / 依存グラフを確認する

### Step 3: プロジェクトルール展開（必須・スキップ禁止）

**このステップを飛ばしてはならない。展開結果は Step 4 の 3 並列 subagent への共通 context となる。**

1. `CLAUDE.md` を読み、記載された規約・禁止事項を**全て列挙**する
2. `.claude/rules/` 内の全ルールファイルを読む
3. `~/.claude/rules/` 内の全ルールファイルを読む
4. 読んだ各ルールに対して、**今回の差分で違反しうる具体的パターン**を列挙する
   - ルールが存在しない場合はそのルールの展開をスキップする
5. 列挙したパターンを観点別 (アーキ系 → 保守性 subagent、性能系 → パフォーマンス subagent、セキュリティ系 → セキュリティ subagent) に振り分け、Step 4 の各 subagent プロンプトに埋め込む

**展開例（hierarchical-architecture）**:

```text
- 依存方向: A→B の import があるが、B→A の逆依存はないか
- 命名: *Manager, *Provider, *Accessor の規則に従っているか
- IF設計: 1インターフェース1責務か。Readable+Writable 混在はないか
- 合成: 2階層超の継承はないか。コンストラクタ注入で合成しているか
- 入力抽象化: Raw→Calibrated→Intent の階層を守っているか
```

**展開例（hallucination-prevention）**:

```text
- 使用API/パッケージは実在するか（公式リファレンスで確認）
- 引数の数・型・順序は正しいか
- 非推奨APIを使っていないか
- ユーザー環境のバージョンで利用可能か
```

**スキルの活用検査も必須** (保守性 subagent に渡す):

```text
- プロジェクトの skills/ に定義された手順を活用しているか
- tdd スキルがあるなら RED-GREEN-REFACTOR を守っているか
- systematic-debugging スキルがあるなら推測修正をしていないか
- premise-questioning スキルがあるなら大規模変更で方針検証を経たか
- feature-pruning スキルがあるなら機能粒度の要否検証を経たか
```

**方針検証観点 (戦略 → 戦術) の追加検査** (保守性 subagent に渡す):

レビュー対象差分が以下に該当する場合、`premise-questioning` / `feature-pruning` の **発動跡**を確認する:

| 検査対象 | 発動必須条件 | スキル参照先 |
|----------|-------------|-------------|
| 戦略 (方針自体) | 100 行以上の変更 / 外部依存追加・削除 / DB スキーマ・公開 API I/F 変更 / バグ修正で根本原因に手を入れる | `~/.claude/skills/premise-questioning/SKILL.md` |
| 戦術 (機能粒度) | UI 機能リスト 5 個以上 / API エンドポイント複数新設 / DB テーブル 5 列以上新設 / 既存機能の削減 | `~/.claude/skills/feature-pruning/SKILL.md` |

**発動跡の判定基準** (いずれか 1 つ以上を満たせば「発動跡あり」と判定):

| 確認対象 | 発動跡と認める記述 |
|----------|------------------|
| PR 本文 | `premise-questioning` / `feature-pruning` / `方針検証` / `✅ 採用` / `skipped (理由: ...)` のいずれかを含む |
| コミットメッセージ | 同上 |
| `.claude/progress.md` の判断ログ | 当該方針の検証結果 (採用 / 撤回 / 修正必要 / skipped) が記録されている |
| 差分中のコメント | 該当箇所に `// premise-questioning: ...` / `# feature-pruning: ...` 等の明示的タグがある |

上記いずれの跡も見当たらない場合、または発動跡があっても結論ラベル (✅ / 🟡 / 🔴 / skipped) が読み取れない場合は **Critical** として指摘する。

該当条件に当てはまるが発動跡が見当たらない場合の指摘テンプレ:

```text
[Critical] 方針検証スキップ
- 該当条件: <100 行以上の変更 / 外部依存追加 / 等>
- 必要 skill: premise-questioning (戦略) / feature-pruning (戦術)
- 確認対象: PR 本文 / コミットメッセージ / .claude/progress.md / 差分内コメント
- 対応: マージ前に該当 skill のワークフローを実施し、結果 (✅ 採用 / skipped 等) を PR 本文に追記
```

### Step 4: 3 並列 subagent dispatch (deep-review コア)

`general-purpose` subagent を **1 メッセージ内 3 並列 (single message, multiple Agent tool calls)** で起動する。逐次起動は禁止 (並列性が失われる)。

#### 共通入力 (全 subagent に渡す)

- Step 1 の差分内容 (全量)
- Step 2 の全体把握サマリー (目的・スコープ・影響範囲・import 依存)
- Step 3 で展開したプロジェクトルール (担当観点に該当する分のみ抽出)

#### 共通出力フォーマット (全 subagent 共通)

各 subagent は以下の形式で findings を返す:

```text
### [Critical|Warning|Suggestion] <カテゴリ名>
- file:line — <問題の 1 行要約>
- ❌ 現状:
  ```<lang>
  <該当コード>
  ```
- ✅ 修正案:
  ```<lang>
  <修正後コード>
  ```
- 理由: <1 文で問題と修正根拠>
```

#### 共通禁止事項

| 禁止 | 理由 |
|------|------|
| 修正コードなしの指摘 | actionable でない |
| 推測指摘 (実コードで確認できない) | 誤検知 |
| 「良い点」セクション | 問題発見に集中 |
| スタイルのみの指摘 | linter / formatter に委任 |
| 担当外観点への侵食 | 後段の重複排除コストが上がる |
| 指摘ゼロの報告で打ち切り | 担当観点を最後まで走査する |

#### 担当割り (3 並列)

##### Subagent 1: セキュリティレビュー

検査観点 (現 code-review カテゴリより):

| 大項目 | 確認内容 | 重要度上限 |
|--------|----------|------------|
| インジェクション | SQL / コマンド / XSS / パストラバーサル / SSRF | Critical |
| 認証認可 | 未認証エンドポイント / 権限チェック漏れ | Critical |
| 機密情報露出 | ログ・レスポンスへの混入 / ハードコード認証情報 | Critical |
| 入力検証 | ホワイトリスト方式 / 長さ上限 / 型 / バリデーションライブラリ使用 | Warning〜Critical |
| 動的コード実行 | 任意コード評価 / 信頼できないデシリアライズ | Critical |
| CORS / CSRF | 過剰なオリジン許可 / トークン欠如 | Warning |
| 依存脆弱性 | 既知脆弱性のあるパッケージ | Warning |
| 暗号・ハッシュ自前実装 | `implementation-policy` 違反 | Critical |
| null 安全性 (セキュリティ起因) | nullable な権限フィールドの未チェック | Critical |
| 並行性起因のセキュリティ | TOCTOU / 共有リソースの非排他アクセス | Critical |

プロンプト雛形:

```text
あなたはセキュリティ専門レビュアーです。下記差分とプロジェクトルールを読み、上記検査観点に該当する問題のみを共通出力フォーマットで列挙してください。
重要度判定は「本番障害・データ漏洩を引き起こしうるか」を基準とする。
担当外の観点 (パフォーマンス・保守性) には踏み込まない。
```

##### Subagent 2: パフォーマンスレビュー

検査観点:

| 大項目 | 確認内容 | 重要度上限 |
|--------|----------|------------|
| N+1 クエリ | ループ内 DB / API 呼出 | Critical |
| 不要な再計算 | キャッシュ可能な重い処理の繰返 | Warning |
| メモリリーク | 解放されないリソース / 肥大化コレクション | Critical |
| 不要なコピー | 大オブジェクトの深いコピー | Warning |
| 非効率なデータ構造 | リスト探索 vs マップ / セット | Warning |
| 並行性・非同期の誤用 | race condition / デッドロック / await 漏れ | Critical |
| 計算量 | 線形・線形対数を超えるアルゴリズム | Warning〜Critical |
| 破壊的 / 後方互換 (パフォ起因) | hot path の I/F 変更による退行リスク | Critical |
| 推測最適化 (`optimize` skill 観点) | 計測なきキャッシュ追加 / 並列化提案など | Suggestion |

プロンプト雛形:

```text
あなたはパフォーマンス専門レビュアーです。下記差分とプロジェクトルールを読み、上記検査観点に該当する問題のみを共通出力フォーマットで列挙してください。
判定根拠は「実行頻度 × データ量 × アルゴリズム計算量」の最悪ケースで述べる。
推測のみで重要度を上げない (実行頻度が不明な場合は Warning 以下に留め、計測推奨を明記)。
担当外の観点 (セキュリティ・保守性) には踏み込まない。
```

##### Subagent 3: 保守性レビュー

検査観点:

| 大項目 | 確認内容 | 重要度上限 |
|--------|----------|------------|
| アーキテクチャ・依存関係 | 依存方向 / 横参照 / 段階飛ばし / 具象依存 / 深い継承 / IF 責務混在 | Critical (依存方向違反) |
| 設計原則 | SOLID / DRY / KISS / YAGNI / 関心の分離 / マジックナンバー | Warning |
| エラーハンドリング | 握り潰し / 汎用キャッチ / 制御フロー利用 / 種別未区別 | Warning〜Critical |
| テスト品質 | テスト欠如 / アサーション不足 / エッジケース / AAA / モック過剰 / 独立性 | Warning |
| 命名・可読性 | 意図不明 / 略語 / 命名規則違反 / 長すぎる関数 / ネスト過深 | Warning |
| モダン性・イディオム | 非推奨 API / レガシー構文 / デッドコード | Warning |
| プロジェクト整合性 | CLAUDE.md / `.claude/rules/` 違反 / 既存パターン無視 | Critical (規約違反) |
| 変更スコープ・互換性 | 破壊的変更 / 後方互換 / スコープ逸脱 | Critical |
| **方針検証発動跡** | premise-questioning / feature-pruning の発動跡 (Step 3 で展開した条件・テンプレを使用) | Critical (発動条件該当時) |

プロンプト雛形:

```text
あなたは保守性専門レビュアーです。下記差分とプロジェクトルール (アーキテクチャ・設計原則・テスト・命名・規約・方針検証発動跡) を読み、上記検査観点に該当する問題のみを共通出力フォーマットで列挙してください。
方針検証発動跡の判定は Step 3 のテンプレを使用する。
担当外の観点 (セキュリティ・パフォーマンス) には踏み込まない。
```

### Step 5: synthesis (3 視点統合)

3 並列 subagent の findings を以下の手順で 1 つのリストに統合する:

1. **重複検出**: 同じ `file:line` の指摘を集約。観点タグを併記 (例: `[セキュリティ / 保守性]`)。
2. **重要度マージ**: 重複指摘の重要度は **最高位を採用** (Critical > Warning > Suggestion)。
3. **優先度ソート**:
   1. Critical (件数降順、同件数なら file:line 昇順)
   2. Warning (同上)
   3. Suggestion (同上)
4. **観点バランスチェック**: 全件が単一観点に偏っていないか確認。偏っている場合は当該 subagent の出力品質を疑い、必要なら **同観点に絞った 1 件追加 subagent** を投入する判断を行う。
5. **冗長削除**: 修正案が同一の重複は 1 件に集約。

### Step 6: 自己検証プロトコル

統合後の指摘リストを出力する前に、以下を全て確認する:

1. **推測での指摘を含んでいないか** — 実コードで確認できない問題を指摘していないか
2. **修正案の構文は正しいか** — 提示するコードが構文エラーを含んでいないか
3. **既存テストへの影響を確認したか** — 修正案が既存テストを壊さないか
4. **存在しない API を使っていないか** — `hallucination-prevention` ルールのパターンを適用
5. **重要度が基準表に準拠しているか** — 重要度パターン基準表と照合し、恣意的な判定をしていないか
6. **アーキテクチャ違反を見逃していないか** — アーキ系ルールが存在する場合、import/依存グラフでルール違反を検査したか
7. **プロジェクト規約との整合性を確認したか** — CLAUDE.md / `.claude/rules/` の規約と変更内容を照合したか
8. **変更スコープが目的に対して過不足ないか** — 目的外の変更混入、または必要な変更の欠落がないか

### Step 7: 出力

下記出力形式に従い、マージ判定とともに統合済みリストを報告する。

---

## 重要度基準

### Critical — マージ不可。必ず修正

本番障害・データ損失・脆弱性を引き起こす、または引き起こしうる問題。

| パターン | 例 |
|----------|----|
| セキュリティ脆弱性 | SQLインジェクション、XSS、コマンドインジェクション、任意コード評価 |
| データ破壊 | 不可逆なデータ変更、トランザクション不整合 |
| 未処理の致命的エラー | 本番でクラッシュする未捕捉例外 |
| 競合状態 | 共有リソースの非排他アクセスによるデータ破壊 |
| アーキテクチャ違反 | レイヤー依存方向逆転、横参照、段階飛ばし |
| 破壊的API変更 | 公開インターフェースの署名変更（既存呼び出し元が壊れる） |
| 規約違反 | CLAUDE.md / `.claude/rules/` の明示的禁止事項への抵触 |
| 方針検証スキップ | 発動条件該当なのに premise-questioning / feature-pruning 発動跡なし |

### Warning — マージ前に対処推奨。3件以上で WARN 判定

バグの温床・保守性低下・技術的負債につながる問題。

| パターン | 例 |
|----------|----|
| 設計原則違反 | SRP違反、DRY違反（3箇所以上）、不要な複雑さ |
| エラーハンドリング不備 | エラー握り潰し、汎用キャッチ、リカバリ不適切 |
| パフォーマンス懸念 | 不要な再計算、非効率なデータ構造 |
| テスト不足 | 変更に対応するテスト欠如、モック過剰 |
| 命名・可読性 | 意図不明な命名、過度に長い関数、深いネスト |
| スコープ逸脱 | 目的外の「ついでに」修正 |
| 既存パターン不一致 | プロジェクト内の慣習と異なるスタイル |
| モダン性 | 非推奨API、レガシーパターン、デッドコード |

### Suggestion — 改善提案。対処は任意

| パターン | 例 |
|----------|----|
| より良いアルゴリズム | 計算量の改善が可能だが現状でも許容範囲 |
| 命名の微改善 | 略語の展開、ブール変数のプレフィックス |
| テスト改善 | AAA準拠、テスト名改善、テストデータの意味明確化 |
| 一貫性の微調整 | 機能には影響しないスタイルの統一 |

**迷った場合は上位の重要度を適用する。**

---

## マージ判定

統合済みリストに対し、以下の基準で判定する。サマリーの先頭に表示すること。

| 判定 | 条件 | 意味 |
|------|------|------|
| **BLOCK** | Critical 1件以上 | マージ不可。Critical を全て解消するまでマージしてはならない |
| **WARN** | Critical 0件 かつ Warning 3件以上 | マージ前に対処推奨。Warning の大半を解消すべき |
| **PASS** | Critical 0件 かつ Warning 2件以下 | マージ可。残件は任意対応 |

---

## 出力形式

### 判定ヘッダー

```text
## 判定: [BLOCK|WARN|PASS]
```

### サマリー

| 重要度 | 件数 | 観点内訳 (セキュリティ / パフォーマンス / 保守性) |
|--------|------|---------------------------------------------------|
| Critical | N件 | x / y / z |
| Warning | N件 | x / y / z |
| Suggestion | N件 | x / y / z |

### 各指摘 (優先度順)

```text
### [重要度] [観点タグ] カテゴリ名
N. ファイル:行 — 問題の要約
```

❌ **現状**:

```言語
// 問題のあるコード
```

✅ **修正案**:

```言語
// 修正後のコード
```

**理由**: 1文で問題と修正の根拠を説明。

---

## 禁止事項 (本 command 全体)

| 禁止 | 理由 |
|------|------|
| 修正コードなしの指摘 | actionable でない |
| 「良い点」セクションの出力 | 問題発見に集中する |
| 推測に基づく指摘 | 誤検知を防ぐ |
| 重要度の過小評価 | 迷ったら上位を適用 |
| スタイルのみの指摘 | linter/formatter に委任 |
| 指摘ゼロの報告 | 常に改善点を探す |
| **3 並列 subagent を逐次起動する** | 並列性が失われる。1 メッセージ内で同時 dispatch すること |
| **担当外観点への侵食を許可する** | 統合フェーズの重複コスト増加 |
