# コードレビュー

直近の変更をレビューする。

## 引数

$ARGUMENTS にレビュー対象を指定（省略時は直近の変更）

## 鉄則

**全指摘に修正コードを添える。修正案なき指摘は指摘ではない。**

---

## レビュー手順

### Step 1: 差分取得

```bash
# 引数があればそれを使用、なければ以下を順に試行
# 1. ステージング済み + 未ステージの変更: git diff HEAD
# 2. 直近コミットの変更: git diff HEAD~1
```

### Step 2: 全体把握

- 変更の目的・スコープを理解する
- 影響範囲を特定する

### Step 3: カテゴリ別検査

下記チェックリストに従い、各カテゴリを順に検査する。

### Step 4: 自己検証

自己検証プロトコルに従い、全指摘を検証する。

### Step 5: 出力

出力形式に従い、結果を報告する。

---

## チェックリスト

### 1. 正確性

| アンチパターン | 確認ポイント |
|---------------|-------------|
| 境界値エラー | off-by-one、空配列、nil/null/undefined |
| エラーハンドリング漏れ | 例外未捕捉、エラー握り潰し、不適切なリカバリ |
| 型不一致 | 暗黙の型変換、any型の乱用、union型の未検査 |
| 競合状態 | 共有リソースの非排他アクセス、TOCTOU |

### 2. 設計原則 (SOLID / DRY / KISS)

| アンチパターン | 確認ポイント |
|---------------|-------------|
| 単一責任違反 | 1関数/クラスが複数の理由で変更される |
| コード重複 | 同一ロジックの複数箇所記述 |
| 不要な抽象化 | 1箇所でしか使わないインターフェース/基底クラス |
| 依存方向逆転 | 下位モジュールが上位に依存 |

**階層型アーキテクチャの場合**: `hierarchical-architecture` ルールを参照し追加チェック:
- 依存方向がピラミッド型（上→下のみ）か
- 同一レイヤー間の直接参照がないか
- 上位が下位の内部状態を直接操作していないか
- 段階を飛ばしたアクセスがないか

### 3. パフォーマンス

| アンチパターン | 確認ポイント |
|---------------|-------------|
| N+1クエリ | ループ内のDB/API呼び出し |
| 不要な再計算 | キャッシュ可能な重い処理の繰り返し |
| メモリリーク | 解放されないリソース、肥大化するコレクション |

### 4. セキュリティ (OWASP)

| アンチパターン | 確認ポイント |
|---------------|-------------|
| インジェクション | SQL/コマンド/テンプレートインジェクション |
| 認証認可欠落 | 未認証エンドポイント、権限チェック漏れ |
| 機密情報露出 | ログ/レスポンスへの秘密情報混入 |
| パストラバーサル/SSRF | ユーザー入力由来のパス/URL未検証 |

### 5. テスト

| アンチパターン | 確認ポイント |
|---------------|-------------|
| テスト欠如 | 変更に対応するテストがない |
| アサーション不足 | `assert True` のみ、戻り値未検証 |
| エッジケース未カバー | 正常系のみ、異常系・境界値テストなし |

## 重要度分類

| 重要度 | 基準 | 例 |
|--------|------|-----|
| Critical | 本番障害・データ損失・脆弱性 | SQLインジェクション、未処理例外、データ破壊 |
| Warning | バグの温床・保守性低下 | 競合状態の可能性、DRY違反、エラー握り潰し |
| Suggestion | 改善の余地 | より効率的なアルゴリズム、命名改善 |

**迷った場合は上位の重要度を適用する。**

---

## 自己検証プロトコル

指摘を出力する前に、以下を全て確認する:

1. **推測での指摘を含んでいないか** — 実コードで確認できない問題を指摘していないか
2. **修正案の構文は正しいか** — 提示するコードが構文エラーを含んでいないか
3. **既存テストへの影響を確認したか** — 修正案が既存テストを壊さないか
4. **存在しないAPIを使っていないか** — `hallucination-prevention` ルールのパターンを適用

---

## 出力形式

### サマリー

| 重要度 | 件数 |
|--------|------|
| Critical | N件 |
| Warning | N件 |
| Suggestion | N件 |

### 各指摘

```
### [重要度] ファイル:行 — 問題の要約
```

❌ **現状**:
```言語
// 問題のあるコード
```

✅ **修正案**:
```言語
// 修正後のコード
```

**理由**: 1文で問題と修正の根拠を説明。

---

## 禁止事項

| 禁止 | 理由 |
|------|------|
| 修正コードなしの指摘 | actionable でない |
| 「良い点」セクションの出力 | 問題発見に集中する |
| 推測に基づく指摘 | 誤検知を防ぐ |
| 重要度の過小評価 | 迷ったら上位を適用 |
| スタイルのみの指摘 | linter/formatter に委任 |
| 指摘ゼロの報告 | 常に改善点を探す |

---

## レビュー後の対応

**基本方針: 全指摘を修正する。**

- レビュー結果の報告後、ユーザーから特に指示がなければ全指摘を修正する
- 修正の優先順: Critical → Warning → Suggestion
- 修正についてユーザーの確認を取る必要はない（指摘した時点で修正案は提示済み）
